# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, and others) when working with code in this repository. It is the single source of truth; `CLAUDE.md` imports it via `@AGENTS.md`.

## Critical rules

These rules affect whether a change can ship at all. They override any other guidance below.

- **DCO sign-off on every commit** — `git commit -s`. CI rejects PRs without `Signed-off-by:`.
- **No `Co-Authored-By: Claude …` trailer or `🤖 Generated with …` footer.** Commit messages and PR descriptions stay human-authored; only the DCO `Signed-off-by:` trailer belongs there.
- **`npm run all` must pass before commit** (clean → build → typecheck → lint → test). CI runs the same chain.
- **Do not regress CLI test coverage.** New code under `cli/src/` is held to 97% statements / 96% branches / 97% functions / 97% lines (see [`cli/vite.config.ts`](cli/vite.config.ts)).
- **Three implementations of the API key parser stay in lockstep.** `parseJolliApiKey` / `assertJolliOriginAllowed` live in [`cli/src/core/JolliApiUtils.ts`](cli/src/core/JolliApiUtils.ts), are bundled into the VS Code extension verbatim, and have a Kotlin port in `intellij/`. Updating one without the others is a known-bad pattern.
- **Editing a skill body means bumping its `metadata.revision`.** The templates in [`cli/src/install/SkillInstaller.ts`](cli/src/install/SkillInstaller.ts) reach disk only when the installed file's revision is *lower* than the template's — **equal skips**, by the same lockstep contract that stops CLI, VS Code and IntelliJ from rewriting each other's `SKILL.md`. The guard never compares content (a hash was rejected: it would make churn-freedom depend on byte-identical output across all three). So changing a body without bumping ships **nothing**: `jolli enable` correctly reports success, and every existing install keeps the old text with no warning anywhere. Rebuilding, or a disable/enable cycle, changes nothing either. Tests pin each body to a fingerprint so this fails loudly — bump the revision *and* update the fingerprint in the same change. `buildPluginJolliMenuSkillTemplate`'s revision must additionally stay **strictly greater** than `buildJolliMenuSkillTemplate`'s: the plugin variant overwrites the bare `/jolli` umbrella in place and depends on outranking it.
- **A dashboard migration is NEVER edited once committed (frozen the moment the PR is pushed), every entry must be re-runnable, and there is no schema version number.** `MIGRATIONS` in [`DashboardDb.ts`](cli/src/dashboard/DashboardDb.ts) is keyed by `name`, applied in array order; the DB logs each touch in `schema_migrations`. Four rules: **①** an entry freezes when the branch is pushed — ship a NEW entry for any delta, never edit / rename / remove one (the log is keyed by name and cannot notice moved bytes, so a DB that logged the old SQL skips the new forever; `SESSION_STATS_SYNC_DDL` did exactly this). Two entries must never share a body (`MigrationFingerprints.test.ts` fails); before "released" is not the line — a pushed branch already reached other machines, and a heal entry ships to every user, so fix your own laptop by hand and amend instead. **②** every entry re-runnable (`CREATE … IF NOT EXISTS`, `INSERT OR IGNORE`, self-excluding `WHERE`); an add-column step goes through `addColumnIfMissing` as a **code entry** (`{name, run}`, no `sql`), everything else via `sqlMigration(name, sql)` — a test runs every entry twice. **③** a code entry has no fingerprint, so it needs a companion `migrations/*.test.ts` asserting each object it creates. **④** no schema version number (`DASHBOARD_SCHEMA_VERSION`, `readSchemaVersion`, the floor keys and `Migration.breaking` were all removed; re-adding any is a review blocker) — "has a newer build written here?" is `verifyMigrationLog`'s unknown-name warning, "maintain the rollup?" is `dbHasUnknownMigrations`, "is schema current?" is `isSchemaCurrent`, all from the log alone. A pre-log DB is REPLAYED (rule ② makes it safe), never version-guessed; nothing refuses a DB. **The runtime byte-compare is gone and re-adding one is a review blocker.** Procedure: "How to add a dashboard migration" below. Full rationale (the `SESSION_STATS_SYNC_DDL` saga, the retired heal entry, the one-time idempotency pass): [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md).

- **The IntelliJ folder reader is RETIRED (cutover gate G.3) — do not reintroduce a plugin-side read path.** [`cli/src/core/FolderStorage.ts`](cli/src/core/FolderStorage.ts) still writes canonical JSON under `<localFolder>/<repo>/.jolli/`, but the plugin no longer reads that tree (or the orphan branch) directly: `FolderStorageReader.kt` and its `shadow-status.json` dirty-marker gate were deleted, and every `SummaryReader` data read goes through the ide-bridge `storage` action (`batch-read` for list-then-read flows, one round trip for N files). The reason is the cutover: any surviving direct read would keep serving plausible-looking stale data after the orphan branch freezes and SQLite becomes the source of truth — worse than no data. Consequences: hidden-layer schema changes no longer need a Kotlin mirror (the old four-path lockstep is void); the plugin inherits whatever backend `createStorage` routes to, so backend changes are CLI-only; and a PR that adds a new direct `git show`/folder read in `intellij/` is a review blocker. Writes stay CLI-only, and the hidden layer remains as the Memory Bank mirror plus recovery source (`doctor --recover` step ②, `.jolli/instance.json` witness — both CLI-owned).
- **The model price table has a second, independent Kotlin copy that must stay in lockstep.** [`cli/src/core/Pricing.ts`](cli/src/core/Pricing.ts) and [`intellij/src/main/kotlin/ai/jolli/jollimemory/core/ModelPricing.kt`](intellij/src/main/kotlin/ai/jolli/jollimemory/core/ModelPricing.kt) each carry the same 32 rows, the same per-model input/output/cached rates, the same `PRICES_AS_OF` stamp (currently `2026-07-30`), and the same rule that a model whose published pricing leaves the cached column blank is priced with its cached segment at the **full input rate**. Adding, repricing or restamping a model in one and not the other makes the same memory cost differently depending on which surface displays it. Two asymmetries are deliberate, not drift: the Kotlin side returns a bare total and drops the unpriced-model set, so the "this total is a lower bound" signal exists only on the TS side; and the Kotlin side adds a Sonnet-rate fallback that TS keeps in `core/TokenCost.ts`. Note the Kotlin per-model lookup is currently **unreachable** in production (the conversation records that surface reads carry no per-message usage, so only its fallback rate is exercised) — keep it in lockstep anyway, since that is a wiring gap and not a decision.
- **A reference source is FIVE declarations, and the JVM host may lag only through `KNOWN_JVM_SOURCE_GAPS`.** Registering a `SourceDefinition` in [`sources/definitions/index.ts`](cli/src/core/references/sources/definitions/index.ts) wires CLI + VS Code only. IntelliJ needs four more: a `SourceId` constant, a `SourceDisplay.Style` whose letter/label/hex equal the [`SOURCE_META`](cli/src/core/references/SourceLabels.ts) row, membership in `PATH_UNSAFE_SOURCES` iff `nativeIdPathSafe:false`, and — for a hyphenated id — the same wire string in `@SerializedName` + `SourceIds.wireName` + `SourceIds.parse`. Each fails silently (Gson decodes an unknown constant to null, so `CommitsPanel` drops the row). `SourceLabelsLockstep.test.ts` holds all five. Deferring the Kotlin is allowed only by adding the id to that test's `KNOWN_JVM_SOURCE_GAPS` (checked both ways, so it must be emptied when the gap closes) — a prose note is not a substitute. IntelliJ's two render paths must stay DERIVED from `SourceId.entries` and `SourceDisplay.of(...).label`, never a hand-written subset.

- **The Cursor plugin is the Codex plugin's structural twin (own `dist/` bundling `cli/src/**`, own marketplace, publish-by-bash, no tests of its own), but its host contract differs in five load-bearing ways that each fail *silently*, so none may be "unified" with the other hosts:** manifest at `.cursor-plugin/plugin.json` / marketplace `.cursor-plugin/marketplace.json`; hook event is camelCase `sessionStart` (a PascalCase key is an event that never fires); `hooks.json` = an array of `{command}` (no `{hooks:[…]}` group); plugin-root var `${CURSOR_PLUGIN_ROOT}` (not an alias — an unexpanded var fails every session); hook output is flat snake_case `{additional_context}`, not `hookSpecificOutput.additionalContext`. `CursorPluginManifest.test.ts` pins all five plus the `hooks.json` event allowlist (an unrecognised event key silently voids the WHOLE file). **All measured rationale for the sub-points below lives in [`cursor-plugin/DEVELOPMENT.md`](cursor-plugin/DEVELOPMENT.md); this is the enforceable summary.**
  - Plugin hooks DO run and their cwd = the plugin dir, so `process.cwd()` is a trap (would install git hooks into the bundle's own checkout) — use `resolveCursorProjectDir` ([`PluginBundlePaths.ts`](cli/src/core/PluginBundlePaths.ts), shared with the MCP guard). Hooks also clear silently unless both `thirdPartyExtensibilityEnabled` and the server gate `enable_cc_plugin_import` are on — hence `run-cli`/`/jolli-init` fallback must stay.
  - Bundle ships the COMPLETE skill set (all twelve, canonical `jolli-` prefix); the `.agents/` duplicate is ACCEPTED and de-dup in that direction is forbidden (only copy Codex/Gemini/OpenCode/Windsurf/Copilot have). Cursor doesn't namespace plugin skills, so `name` must equal the directory and a stray `metadata.surfaces/environments/scopedTo` key silently hides a skill (`CursorPluginSkills.test.ts`). Retired mirror survives as a one-way sweep (`removeCursorRepoSkills`, ownership-guarded).
  - The `jolli` umbrella is bundled; machine-global `~/.cursor/skills/jolli/` is RETIRED and re-adding it is a review blocker (a fresh plugin's hooks don't register until Cursor FULLY restarts, so the global copy couldn't survive its own install). Remains a one-way sweep (`removeCursorGlobalMenu`, `UninstallScan.scanCursorGlobalMenu`); `resolveCursorProjectDir` rejects `""` by `trim().length===0`.
  - This host does NOT auto-install into a repo — only one of three — gated on `isGitHookInstalled(worktreeRoot)` (WORKTREE, never the machine); `workspaceOpen` fires for every sidebar repo. Setup is `/jolli`→`jolli-init`; `reconcileRuntimeRegistry` + the `removeCursorGlobalMenu` sweep run unconditionally in `main()` ahead of any repo.
  - `dist-paths/<tag>` records a RUNTIME keyed by source tag alone, never a bundle location — don't reach for it to locate one, and don't make the registry refuse a foreign runtime's write (re-opens the stale-worktree bug). Retired `cursor-plugin-root` is gone; the lesson isn't.
  - The `stop` hook's one critical job is WHICH source: `resolveCursorSource` reads `CURSOR_INVOKED_AS === "cursor-agent"` first, else probes `~/.cursor/chats/<hash>/<uuid>/`, because `cursor`/`cursor-cli` share a transcript but index into two disjoint discoverers and a mis-tag sits BESIDE the real row, silently doubling tokens. Ignores per-generation `input_tokens`/`model`. [`CursorStopHook`](cli/src/hooks/CursorStopHook.ts) adds no extraction logic.
  - Two Cursor readers chosen by PATH SHAPE; a bare `readCursorTranscript` call is a review blocker (an IDE composer's `agent-transcripts` JSONL has no `#composerId` and throws, which both bypassing call sites swallowed into a silent empty transcript). Share `isCursorJsonlTranscript`.
  - `allSessions` in `QueueWorker` is deduped on `(source, sessionId)`; removing it is a review blocker (a hook-poor source that gains a lifecycle hook arrives by two routes and the double-read accumulates the identical slice with pre/post counts that double together).

- **The Node ≥ 22.13 floor is a five-place lockstep.** `node:sqlite` throws on import until 22.13 without `--experimental-sqlite`, which the VS Code host and the flag-free git-hook dispatchers can never supply — so every surface that provides/resolves a runtime must agree or a hook DB write throws where it lags: `cli/package.json` `engines.node`, [`SqliteHelpers.ts`](cli/src/core/SqliteHelpers.ts) `NODE_SQLITE_MIN_VERSION`, `vscode/package.json` `engines.vscode` (^1.101.0) + its esbuild `target`, [`NodeRuntime.kt`](intellij/src/main/kotlin/ai/jolli/jollimemory/bridge/NodeRuntime.kt) `MIN_SUPPORTED_MAJOR`/`MIN_SUPPORTED_MINOR`, and the Claude plugin's [`build.mjs`](claude-plugin/plugins/jolli/scripts/build.mjs) `target`. The hook write degrades gracefully below the floor (skip, never block git).
  - **The Codex & Cursor plugins invert the skill-revision trap: their skills are committed static files, so editing a shared builder means RE-RUNNING each generator or the copy silently keeps old text** — `npx tsx codex-plugin/plugins/jolli/scripts/generate-skills.ts` and the Cursor equivalent. Four builders (`recall`/`search`/`local-run`/`remote-run`) feed THREE artifacts: bump revision + fingerprint for the installed copy AND regenerate both bundles (`CodexPluginSkills.test.ts` / `CursorPluginSkills.test.ts` fail on drift). The two shared transforms live in [`PluginSkillText.ts`](cli/src/install/PluginSkillText.ts); the Codex render rewrites siblings to `jolli:<name>`, so never put a path-shaped `jolli-<name>` string in a shared builder (a plain substring replace would corrupt it).
  - `buildDashboardSkillTemplate` is a fifth shared body, deliberately NOT one of the four: no `metadata.revision`, no fingerprint (nothing upserts it), so an edit = regenerate both bundles (two artifacts); the Claude plugin's `/jolli:dashboard` is a fourth hand-written copy.
  - `SHELL_PREREQUISITE_BLOCK` (same module) is triggered by shelling `run-cli`, not the here-doc — `run-cli` is a bash script only Git Bash's `$HOME` resolves, so PowerShell fails with a plain "not recognized". Both bundles carry it on `jolli`/`init`/`login`/`logout`/`status`/`dashboard` (drift tests derive the requirement from the body); keep it free of path-shaped `jolli-<name>` strings.

- **The global daemon's trigger must never wait on the daemon's event loop, and a retiring trigger must never spawn its replacement.** [`EnsureGlobalDaemon.ts`](cli/src/daemon/EnsureGlobalDaemon.ts) is called from five sites (CLI tail, `post-commit`, `SessionStart`, both plugin bootstraps); `connect()` is kernel-bounded but reading `hello` waits on the daemon's synchronous `VACUUM INTO` (measured 547 ms), hence the 300 ms hello budget whose timeout means DO NOTHING (a successful connect already proved a listener). The retire path stops at `retire` — the retired daemon still holds the socket, so an immediately-started replacement dies `EADDRINUSE` silently; the next trigger respawns. `uninstall`/`disable` are excluded (keyed off `getInvokedRootCommand`, never argv position); `uninstall` sends `retire` ONLY when it removed a machine-global surface (every daemon task is machine-wide, so a repo-scoped uninstall retiring it would stop them for every other repo). Five sites + the retire are pinned by a source-shape test.
  - **Neither daemon's trigger may spawn `process.argv[1]`** — argv[1] is the CLI entry only when the caller IS the CLI, but four triggers run from a hook entry, so spawning argv[1] re-runs that hook against `homedir()` unbounded (and if `$HOME` is a git repo, `runPluginBootstrap` installs Jolli into it). Both spawns go through [`resolveCliEntry`](cli/src/util/CliEntry.ts) (finds `Cli.js` beside the caller's `import.meta.url`; it is in `REQUIRED_RUNTIME_FILES`), carrying `launchWorker`'s `existsSync` guard for the `tsx`-against-source case.

- **`TaskScheduler` holds no persistent state, and adding some is a review blocker.** `tickIntervalMs` is how often to ASK a task whether it is due, not how often it acts: `maybeSnapshot` already gates itself on `last-snapshot-at` in `schema_meta`, so a scheduler-owned `lastRun` would be a second owner of one fact with no tie-breaker. Downtime catch-up and post-retire handover both work *because* of this — every task is ticked once at startup and answers for itself. Note the timers are `unref`'d (the listening socket keeps the process alive), which is the OPPOSITE of `McpProxy`'s retry timer, where the timer is the only handle.
- **`.jolli/manifest.json` and `.jolli/index.json` stay in lockstep with the IntelliJ Memory Bank reader.** [`cli/src/core/FolderStorage.ts`](cli/src/core/FolderStorage.ts) writes canonical JSON under `<localFolder>/<repo>/.jolli/` (`summaries/<hash>.json`, `plans/`, `notes/`, and the `index.json` manifest). One Kotlin reader still parses part of that tree directly: [`KBFolderReader.kt`](intellij/src/main/kotlin/ai/jolli/jollimemory/core/KBFolderReader.kt) natively deserializes `.jolli/manifest.json` (to `Manifest`) and `.jolli/index.json` (to `SummaryIndex`) for the Memory Bank sidebar's hot path, and `KBExplorerPanel` enumerates commit hashes from `index.entries`. Schema changes to either file, or to the Kotlin DTOs mirroring them, MUST update `KBFolderReader.kt` in the same PR. Writes stay CLI-only (dual-write consistency).

  This reader is a **narrow, measured exception** to the rule below, not a precedent: it exists because a per-read `git show` subprocess is too slow for a sidebar hot path, and it only deserializes files. Nothing about "which rows are visible" or "what a delete also removes" lives in it. Its retired sibling `FolderStorageReader.kt` — which read `summaries/`, `plans/`, `notes/`, archived references and the `shadow-status.json` dirty marker — was **deleted** at cutover gate G.3; see the retirement rule above, and do not restore either it or the dirty-marker gate.

- **IDE hosts are adapters — product rules (what data MEANS: which rows are visible, what an archive guard is, whether removing a row unlinks its file, what a commit claims) live in `cli/src/core`, never the host.** VS Code imports them in-process; IntelliJ calls `jolli ide-bridge`. Host side is presentation only (row layout, icons, dialogs, keys). The asymmetry is the reason: a Kotlin restatement of a CLI rule fails *silently* — Gson drops unknown fields and writes null into known ones — and stays wrong until a user reports it (every drift found sinking the plan/note services shipped this way). Full discard/plans/notes catalogue + rationale: [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md).
  - Working-context rules live in [`PlanService`](cli/src/core/PlanService.ts) / [`NoteService`](cli/src/core/NoteService.ts) / [`ReferenceService`](cli/src/core/references/ReferenceService.ts); `vscode/src/core/{Plan,Note}Service.ts` are re-export shims — adding a function to a shim hides it from IntelliJ. IntelliJ reaches them via the `working-context` ide-bridge action ([`IdeBridgeCommand.ts`](cli/src/commands/IdeBridgeCommand.ts)); never reintroduce Kotlin-side registry mutation/filtering.
  - `detectPlans`/`detectNotes` (browsable panel; a revived committed row stays visible) vs `active-for-commit` (archive set; only rows no commit has claimed) are NOT interchangeable — never post-filter either in the host.
  - [`FileDiscardService`](cli/src/core/FileDiscardService.ts) owns every index/worktree combination: six groups `unmerged`/`renamed`/`added`/`untracked`/`staged-worktree`/`worktree-only` (a copy rides inside `added`), and `classifyEntry` tests `unmerged` FIRST (`AA`/`AU` also carry an index `A`, so any other order deletes a file HEAD still has). **Callers pass PATHS, never status codes** — the service resolves each from one authoritative `git status`, which is what makes the drift structurally impossible.
  - Those paths are WORKTREE-ROOT-relative; IntelliJ anchors via [`WorktreeRoot.of`](intellij/src/main/kotlin/ai/jolli/jollimemory/core/WorktreeRoot.kt) (=`GitOps.resolveWorktreeRoot`, NOT `project.basePath`). A path git has no entry for answers `not-found`+`ok:true` — a silent success.
  - **A failed discard must reach the user: branch on `ok:false`, never on `error` being non-empty** (`error` is nullable). `not-found` is the ONLY always-`ok:true` action; a failed status read is `status-unavailable`, a blank path is `invalid-path`, an unrecordable path is `unclassified` (all distinct from `not-found`). `FileDiscarder` synthesises one FAILED outcome per path when the body is unparseable / miscounted / has a blank `action`.
  - **Paths reach git as `:(literal)` pathspecs — NOT only a discard rule** (a bare path globs: `git restore -- 'a[1].txt'` reverts `a1.txt` and exits 0). Helper [`literalPathspec`](cli/src/core/GitOps.ts) + hand-kept Kotlin mirror; apply wherever a path came out of git or a UI row, never to a caller-authored pattern. Not yet honoured everywhere (known unwrapped: `sync/GitClient.ts`, `diffForSelection`, `getWorkingTreeDiffStats`).
  - After a discard IntelliJ must `refreshIoFiles` every path in `DiscardOutcome.touchedPaths` (a rename revert restores its original too, reported in `additionalPaths`), and flush the clicked path's unsaved editor edits BEFORE the call ([`UnsavedEdits`](intellij/src/main/kotlin/ai/jolli/jollimemory/core/UnsavedEdits.kt), requested paths only). VS Code needs neither.
  - **Gson absent-field behaviour depends on the CLASS**: a data class with a default on EVERY primary-ctor param gets a no-arg ctor (defaults run); otherwise `Unsafe.allocateInstance` runs NO default (non-null fields land null, throw on read). Declare an omitted mirror field **nullable** — correct under both regimes; don't "simplify" it to non-null-with-default.
  - One path can produce TWO status rows (`git rm --cached` → `D`+`??`); `readStatus` resolves by PRECEDENCE not arrival order (untracked never displaces an existing entry).
  - The confirmation verb is `previewDiscard`'s answer (shares `classifyEntry`, read-only, over `discard-preview`), NOT a status letter — the collapsed one-letter status is lossy (`D `/`DU`/`DD` all arrive `"D"`). `discardDeletesFile` survives only as the fallback for when the query itself throws; it must cover untracked/index-added/renamed/copied (`C` IS emitted with `status.renames=copies`; the `-z` stream reverses the rename pair).
  - A capability VS Code reaches by import but that has no `working-context` operation is silently "VS Code only" (mid-session plan discovery shipped that way for a year) — the fix is a bridge op in `IdeBridgeCommand.ts`, never Kotlin. Performance is not a reason to re-implement (daemon-backed bridge = 5-20 ms).

- **Working-area context belongs to the worktree, not to a branch.** Uncommitted plans, notes, references and Conversations follow the user across `git checkout` and bind to a branch only at commit (recorded on `CommitSummary.branch`) — exactly like an uncommitted code change. `plans.json` therefore carries no `branch` on these rows: `LEGACY_PLAN/NOTE/REFERENCE_FIELDS` in [`SessionTracker.ts`](cli/src/core/SessionTracker.ts) strip it on every load→save, alongside the other dead fields (`ignored`, `editCount`) — and an `ignored: true` row is **dropped wholesale**, so writing that field is a hard delete, not the soft one its name suggests. Do not add a `branch` field to a working-area row, stamp one on a creation path, filter a panel by one, or label a row with one. The Kotlin mirrors in [`core/Types.kt`](intellij/src/main/kotlin/ai/jolli/jollimemory/core/Types.kt) and [`references/ReferenceTypes.kt`](intellij/src/main/kotlin/ai/jolli/jollimemory/core/references/ReferenceTypes.kt) must stay field-for-field with the CLI's `PlanEntry` / `NoteEntry` / `ReferenceEntry`; a field the CLI strips deserializes to null forever, and a non-nullable declaration of one throws.
- **Cross-package imports in `vscode/src/**` are intentional.** Paths like `../../../cli/src/core/JolliApiUtils.js` resolve at esbuild bundle time. Don't refactor them into a published-package import — VS Code currently bundles the CLI inline.
- **Every orphan-branch write holds `orphan-write.lock`; a new unlocked write path is a review blocker, and a bare `acquireOrphanWriteLock` call is one too — always through a wrapper.** Only the wrappers register [`OrphanWriteReentrancy.ts`](cli/src/core/OrphanWriteReentrancy.ts)'s async-context store, and the lock refuses even its own PID, so a hand-rolled acquire self-blocks and reports *contention* — a silent write-never-lands whose log line reads like normal contention. Pick by failure policy: `withRequiredOrphanWriteLock` (must land, 30 s, throws the typed `OrphanWriteBusyError`), `withDeferrableOrphanWriteLock` (background, answers `onBusy()`), `Locks.withOrphanWriteLock` (general). Topic/processed-source stores, both compile `writeGuard`s and the ide-bridge writes use the must-land form ([`SummaryStore.ts`](cli/src/core/SummaryStore.ts)) — none has a re-invocation. The single exemption is the cutover CAS (holds N sources' locks at once, documented in place). As its last line `OrphanBranchStorage.writeFiles` re-reads the cutover fence from disk immediately before the plumbing write and throws if frozen.

- **The cutover's step-3 compare is a REPORT, not a gate — restoring the veto is a review blocker.** `compareSourceContainment` ([`CutoverEngine.ts`](cli/src/dashboard/CutoverEngine.ts)) collects every path the frozen tip lists that the DB does not reproduce, records `CutoverRecord.unreconciled`, and PROCEEDS to the fence + CAS. The gate is step 2 (`importRepoMemory` throws on a real fault). Forced by measurement: a real branch carries paths the import can NEVER store, so refusing stranded the repo forever, while the fence FREEZES (not deletes) the branch — every unreconciled path stays readable and `jolli cutover --status` prints it (paths de-duplicated across sources; real tips shown via `git -C <root> show <tip>:<path>`; the commit run's list is uncapped, `--status`/log stop at 50). **Two IMPORT refusals survive and must stay — removing or merging either is a review blocker:** ① `summaries/` listed and zero summary rows → refuse; ② any of the eight families listed and zero rows of every kind (`storedNothing`) → refuse. Neither may become a per-family veto or a compare ratio (both strand a repo on one un-importable item). A repo with no orphan branch pins `NO_ORPHAN_TIP` (`""`) and cuts over (imported from `EMPTY_ORPHAN_STORAGE`); fold `resolveCommittish`'s null onto that sentinel in every later tip comparison.

- **Worktree-aware code only.** Hooks, summary storage, and lock files must work across `git worktree` checkouts. Don't assume a single working tree.
- **`.jolli/` is excluded entry-by-entry, and `.jolli/agents.json` is committed.** That one file records decisions about *this* repo (verify gate, base branch, directory layout) that a teammate cannot regenerate; everything else under `.jolli/` is per-developer state. The ordering and the trailing `/*` in `.gitignore` are load-bearing — a bare `.jolli/` stops git descending, and a negation cannot re-include a file whose parent was never entered. Nested `*/.jolli/` stays excluded.

- **The `local-agent` provider drives one of six CLIs** (`localAgentTool`: `claude-code` | `codex` | `cursor-agent` | `opencode` | `kimi` | `hermes`, default first). Only `claude-code` is capability-probed with real run flags; `opencode` keeps provider creds in the child env (spends the user's own credit, no auth-failure classification). Full measured rationale (every flag/refusal/isolation lever): [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md).
  - **Model is pinned PER TOOL, only for a tool that declares one (`claude-code`, `codex` today)** via `LOCAL_AGENT_TOOLS[…].models` ([`ToolMeta.ts`](cli/src/core/localagent/ToolMeta.ts)); `resolveLocalAgentModel` returns `""` (= emit no model flag) otherwise. Never hard-code a tool id in a surface. Pinning a third tool = that one table PLUS a refusal classifier in its backend.
  - **The default is a property of the TOOL (`defaultModel`/`localAgentToolDefaultModel`), never one global constant** (`DEFAULT_LOCAL_AGENT_MODEL` is claude-code's) — a shared fallback emits one CLI's id at another's namespace (400). `pickLocalAgentModel` is the single core; panels mark the default by marker not position; VS Code selects the tool's `inherit` by INDEX (several `<option value="inherit">` exist; `select.value` picks the first).
  - **Both Settings payloads carry the RAW stored model; display resolution is the CLIENT's job** — a server-resolved value round-tripped destructively (opening Settings under codex rewrote a claude `opus`). `effectiveLocalAgentModel` was removed; only `resolveLocalAgentModel` (runner) remains.
  - **codex ids are dated slugs, not aliases**, so the list needs a release each codex generation; fetching it was measured-and-rejected (undocumented, ~2.2s, silent fallback list wrong both ways). Unpinned was reverted (a background workload silently rode the dev's interactive model — measured `claude-opus-5[1m]`, ~73% of a 5h window). Default = each tool's mid-tier (`sonnet` / `gpt-5.6-terra`), overridable by `localAgentModel` (a DIFFERENT field from `model`), `"inherit"` = explicit opt-out.
  - **A refused model → ONE un-pinned retry in `callLocalAgent`, keyed on `LocalAgentModelRefusedError` alone — NOT the optional-flag machinery** (a refused model exits 1 writing `{api_error_status:404}` to STDOUT, surfacing in `parseResult` downstream of the degradation loop). **Every pinned tool must classify its own refusal** or the retry never fires. codex classifies STRUCTURALLY (JSON envelope in `message`, HTTP status, quoted model id), returning 401/403/429/5xx ahead of the 4xx range check.
  - **`modelUsage` is NOT single-entry** (claude runs an unswitchable helper turn); `pickModel` prefers the entry naming the requested alias, else highest TOTAL INPUT. `LocalAgentOutcome.model` carries only a model a backend can PROVE it ran (claude via `modelUsage`); codex records the REQUESTED id and skips the requested-vs-actual warning.
  - **Isolation flags are optional by construction — never add one unconditionally, never to `probeArgs`** (an unknown flag exits non-zero before running → "every summary fails" non-retryably; `claude` pre-scans `--version` so a probe can't validate it anyway). Declare in `optionalFlags` ([`OptionalFlags.ts`](cli/src/core/localagent/OptionalFlags.ts)); `LlmClient` drops-and-retries on `LocalAgentSetupError`, recording under `agent-unsupported-flags.json` keyed `<tool>@<version>` (needs a real `extractProbeVersion` — codex prints `codex-cli 0.146.0-alpha.3`). Three invariants: nothing persisted until a degraded run SUCCEEDS; a success records only flags the CLI NAMED (opt-out `unnamedFlagFailures` = opencode alone); only `LocalAgentSetupError` degrades.
  - **A run with no answer MUST throw — returning `""` is a data-loss bug** (codex's out-of-credits shipped silently; Regenerate overwrote a good summary with empty while printing success). Backend throws on its own failure envelope AND `LlmClient` rejects an empty completion from any tool; neither throws `LocalAgentSetupError`. codex classifies on the EVENT reason (`turn.failed` throws on sight; an `error` event is a candidate, thrown at stream end only if no assistant text arrived); reason carried on `CaptureEventData.llmFailure` (ANSI-stripped).
  - **Per-tool isolation levers (each measured; plausible ones are traps):** claude `--strict-mcp-config --disable-slash-commands --setting-sources ""` (NOT `--bare`, which kills the keychain OAuth); codex `--disable plugins` (NOT `-c …={}` no-ops, NOT `--ignore-user-config` which drops the user's model); opencode `OPENCODE_DISABLE_CLAUDE_CODE=1 --pure`; hermes `--ignore-rules` (NOT `--safe-mode`, which implies `--ignore-user-config` and takes their provider key). Verify against the tool's own state output, never a vanished error line.
  - **`hermes`**: accounting arrives BESIDE stdout (`--usage-file`; `parseResult` gained a `cwd` param; an absent report = no accounting, not a failed run); argv is the ONLY prompt channel; deliberately UNPINNED (`provider/model` ids). **`kimi`** (`@kimi-code/cli`): scrubs `MOONSHOT_API_KEY`, reads `stream-json`; prompt is size-adaptive — above `KIMI_ARGV_PROMPT_BUDGET` (24 KB) written to `<cwd>/jolli-context.md` via `--agent-file` (requires YAML frontmatter). IntelliJ carries a hand-maintained mirror [`LocalAgentTools.DEFAULT_TOOLS`](intellij/src/main/kotlin/ai/jolli/jollimemory/core/LocalAgentTools.kt) — editing `LOCAL_AGENT_TOOLS` MUST update it (`LocalAgentToolsTest`).

- **Every dashboard table must appear in exactly one of the two session-sync lists — the partition IS the privacy boundary.** `SYNCED_TABLES` / `NEVER_SYNCED_TABLES` ([`SessionPushManifest.ts`](cli/src/dashboard/SessionPushManifest.ts)) cover `sqlite_master` both ways, with a two-tier regex net over every column name: tier 1 (`/transcript|content|body|text/i`) exempts nothing; tier 2 (`/query|prompt|message|title|term|snippet|excerpt|description|instruction/i`) requires a ≥40-char reason in `FREE_TEXT_EXEMPTIONS` (keep tier 2 SHORT — each speculative token costs a meaningless exemption). The server repo carries the mirror (`JolliMemorySessionColumns.test.ts`). A synced table's primary KEY travels too, so don't interpolate an unbounded column into it — `memory_lookups.receipt_id` uses a fixed-length [`lookupQueryFingerprint`](cli/src/dashboard/DashboardModel.ts) (server caps `receipt_id` at 500 vs `query` at 20 000; a long query otherwise 400s the whole all-or-nothing channel). Adding a table to [`SotSchema.ts`](cli/src/dashboard/SotSchema.ts) unclassified fails `SessionPushManifest.test.ts`; a synced table also needs `SYNC_STAMP_COLUMNS` + `KEYSET_COLUMNS` + `WINDOW_SOURCES` ([`SyncColumns.ts`](cli/src/dashboard/SyncColumns.ts)). Stamp names aren't uniform (`sessions`/`commits`: `written_at_ms`; child tables: `updated_at_ms`) and a NULL/stale stamp is invisible to every cursor forever.

- **Suspected vulnerabilities go through [`SECURITY.md`](SECURITY.md)**, not public issues or PRs.
- **Workflow injection hygiene.** Inside `.github/workflows/*.yaml`, any `${{ … }}` expression derived from a user-controlled context — `github.event.*`, `inputs.*`, `github.head_ref`, the commit author/message fields, etc. — must be funnelled through `env:` before reaching a `run:` block or the `with:` of an untrusted action. Direct interpolation is the injection pattern. The existing publish workflows already follow this for both `inputs.tag` and `github.event.release.tag_name`.

## Repository layout

Monorepo with six deliverables that share the same product model and storage. By default (0.99.0+) every memory is dual-written to **both** the git orphan branch `jollimemory/summaries/v3` (system of record) and the user-pickable **Memory Bank** folder on disk. The Memory Bank folder has two layers: a hidden `<localFolder>/<repo>/.jolli/` directory holding canonical JSON (`summaries/<hash>.json`, `transcripts/<hash>.json`, `index.json`) for programmatic access, and a visible `<localFolder>/<repo>/<branch>/<slug>-<hash8>.md` layer holding human-browsable Markdown for the user. Reads come from the orphan branch:

- `cli/` — `@jolli.ai/cli` (npm workspace, Node 22.13+, ESM, Vite multi-entry lib build). Standalone command-line tool plus all git/agent hook scripts.
- `vscode/` — `jollimemory-vscode` extension (npm workspace, esbuild → CJS). Bundles the CLI and hook scripts into its own `dist/` so it has **no dependency on a global CLI install**.
- `intellij/` — separate Gradle/Kotlin project (JDK 21). Independent build, but installs the same git/agent hooks and writes to the same shared state: the orphan branch, the Memory Bank folder, the machine-global `~/.jolli/jollimemory/` (config + hook entry scripts), and the per-project `<projectDir>/.jolli/jollimemory/` (sessions, cursors, queue, …).

- `claude-plugin/` — the Claude Code plugin (`claude-plugin/plugins/jolli/`, esbuild → CJS via `scripts/build.mjs`). Bundles the same `cli/src/**` into its own `dist/`, registers the MCP server via its `.mcp.json`, and installs the canonical Stop/SessionStart hooks from a single `PluginBootstrapHook`. Built and gated by the root `npm run all` chain like the other deliverables, but it has **no publish workflow**: releases are the bash scripts in `claude-plugin/scripts/`, which mirror it into a separate marketplace repo.
- `codex-plugin/` — the Codex plugin (`codex-plugin/plugins/jolli/`, same esbuild shape, `__JOLLI_CLIENT_KIND__` = `"codex-plugin"`). Structurally the Claude plugin's sibling — own `dist/` bundling `cli/src/**`, own marketplace, publish-by-bash-script — with four differences worth knowing before touching it:
  - **Manifest lives at `.codex-plugin/plugin.json`** and its marketplace at `.agents/plugins/marketplace.json`. That second path is why `.gitignore` needs `!/codex-plugin/.agents/` *before* any pattern inside it: `.agents/` is broadly ignored (Jolli writes `.agents/skills/` into user repos) and git never descends into an excluded directory, so a re-include of a file under it cannot match until the directory itself is un-excluded.
  - **One manifest hook, no MCP entry.** `hooks.json` registers only `CodexPluginBootstrapHook` (via `${PLUGIN_ROOT}`, Codex's own variable). MCP is registered into the global `~/.codex/config.toml` instead — see the `--repo-hooks-only` exception under "MCP server registration" for the measurements behind that.
  - **The hook's stdout must be exactly one JSON object in the `hookSpecificOutput` envelope** — `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}`. Codex validates against a schema embedded in its own binary (`session-start.command.output`, `additionalProperties: false` at both levels, `hookEventName` required), so a flat `{additionalContext}`, a missing `hookEventName`, or ANY non-JSON byte on stdout fails the whole hook. That failure is invisible where it matters: the bootstrap's side effects (repo hooks, MCP registration) still land, so the install looks healthy while `codex exec` prints one more `hook: SessionStart Failed` among the unrelated ones and the briefing silently never reaches the model. Both mistakes shipped at once — the flat shape, and `SessionStartHook.main()` self-running inside the bundle and printing plain text ahead of the JSON. Verify with `codex exec` and look for `hook: SessionStart Completed`, not by checking that hooks got installed.
  - **Its skills are committed static files, generated from the CLI's builders.** `CODEX_PLUGIN_SKILLS` in [`cli/src/install/CodexPluginSkills.ts`](cli/src/install/CodexPluginSkills.ts) is the source of truth; `scripts/generate-skills.ts` is a thin runner over it. Editing a shared builder in `SkillInstaller.ts` therefore changes TWO artifacts, and the committed copy only moves when you re-run the generator.
  - **Host isolation is load-bearing.** Its bootstrap shares `install(..., { repoHooksOnly: true })` with Claude's but must never write `.claude/**`; the split is driven by the source tag through `pluginBootstrapHost` ([`cli/src/core/localagent/PluginDefaults.ts`](cli/src/core/localagent/PluginDefaults.ts)), not by the compile-time client kind, because the `/jolli:init` path dispatches through `run-cli` and can land in a `cli` bundle.

- `cursor-plugin/` — the Cursor plugin (`cursor-plugin/plugins/jolli/`, same esbuild shape, `__JOLLI_CLIENT_KIND__` = `"cursor-plugin"`). The Codex plugin's structural twin; see the critical rule above for the five host-contract differences that must not be unified, and [`cursor-plugin/DEVELOPMENT.md`](cursor-plugin/DEVELOPMENT.md) for the open questions still to be closed by a probe before release.

Three lists describe the Codex plugin's `dist/` and must move together, or the failure is a **blocked user commit** rather than a missing feature (a git hook resolving to `node <missing file>` aborts the git operation): `entryPoints`/`EXPECTED_ENTRY_OUTS` in [`codex-plugin/plugins/jolli/scripts/build.mjs`](codex-plugin/plugins/jolli/scripts/build.mjs), `PUBLISH_REQUIRED_DIST` in [`codex-plugin/scripts/_publish-lib.sh`](codex-plugin/scripts/_publish-lib.sh), and `REQUIRED_RUNTIME_FILES` in `DistPathWriter.ts`. The bundle ships hooks this host never installs (Claude's Stop/SessionStart) precisely because dist completeness is a machine-global contract: an incomplete dist is refused registration, and a *registered* one that wins the version race has to be able to serve every other host's repo hooks. `McpLauncher.js` is the one entry deliberately **outside** `REQUIRED_RUNTIME_FILES` — only this bundle ships it, and promoting it would make every already-installed dist fail the completeness check and de-register itself. A parallel pair covers the skills: `CODEX_PLUGIN_SKILL_NAMES` and `PUBLISH_EXPECTED_SKILLS`, asserted equal by `CodexPluginManifest.test.ts` (an exact set, never a glob — this repo has already lost a `SKILL.md` to a gitignore rule while `git add` reported success). The **Cursor plugin carries the same four lists** under `cursor-plugin/`, asserted by `CursorPluginManifest.test.ts`; its `PUBLISH_REQUIRED_DIST` is one entry shorter because it ships no `McpLauncher.js`, and its `PUBLISH_EXPECTED_SKILLS` is the complete eleven (it once had a fifth list, `PUBLISH_EXPECTED_MIRROR`, retired with the per-repo skill mirror).

Root `package.json` coordinates five build targets: the `cli` and `vscode` npm workspaces plus the three non-workspace plugin builds (`npm run build` chains `build:cli` → `build:claude-plugin` → `build:codex-plugin` → `build:cursor-plugin` → `build:vscode`). It does not touch `intellij/`. All three plugin globs are in [`build-vscode.yaml`](.github/workflows/build-vscode.yaml)'s path filter because that job is the ONLY gate that builds them — without the globs a plugin-only PR reports success having compiled nothing. Use `.nvmrc` (currently `24.10.0`) for the Node version.

Before releasing any plugin, confirm the server accepts its `__JOLLI_CLIENT_KIND__` (`claude-plugin` / `codex-plugin` / `cursor-plugin`) — the surface self-identifies with it on the wire and min-version gating routes on it.

**Names you'll see (all refer to the same product):**

- **`jollimemory`** — product name; orphan branch prefix (`jollimemory/summaries/v3`).
- **`jolliai`** — current GitHub org / repo namespace (`github.com/jolliai/jolliai`).
- **`@jolli.ai/cli`** — npm scope and package name for the CLI workspace.
- **`jollimemory-vscode`** — `package.json` `name` of the VS Code extension. Root npm scripts reference it via the **workspace path** `vscode` (e.g. `npm run test -w vscode`), not by package name.

From the repo root (npm workspace; coordinates `cli` + `vscode`):

```bash

npm run build          # build cli, then the Claude Code and Codex plugins, then vscode (all three bundles inline cli/src/**)
npm run typecheck      # tsc --noEmit in both

npm run test           # vitest run --coverage in both (cli 97/96/97/97, vscode 97/97/97/97 — both enforced)
npm run all            # clean → build → typecheck → lint → test (use before committing)
```

`npm run all` is the **pre-commit gate, not the inner loop** — the CLI suite is 504 files / 3.5-10 min with coverage depending on machine load (499 unit under `cli/src/`, plus 5 acceptance under `cli/test/sync-acceptance/`), alongside the 110-file vscode suite. **Every file count here is a measurement, not a contract — re-derive it rather than trusting it; the last set went ~50 files stale before anyone noticed.** The cost is concentrated: the **22 real-`git`/real-fs files in `SLOW_TEST_FILES` carry the bulk of the runtime** against a ~14 ms median file, so the tiers split along that line. Inner loop: `npm run test:fast` (the remaining light CLI files **with coverage**), then `npm run test:slow` when you touch `sync/`, `install/`, or git plumbing. Both exist at the repo root and delegate to the `cli` workspace; `test:fast` covers **CLI only** — the vscode suite has no tier worth carving (110 files, ~54 s with coverage), so run `npm run test:vscode` whole when you touch `vscode/`. `test:fast` runs as `vitest --mode fast`, which drops the slow test files *and* the source files they are responsible for (`SLOW_TEST_FILES` / `SLOW_ONLY_SOURCES` in `cli/vite.config.ts` — read both lists there rather than quoting a length) so the 97/96/97/97 thresholds stay enforced instead of failing on an absent denominator. That coverage exclusion must never leak out of the `fast` branch — in the gate it would silently stop the floor from protecting `sync/` and `install/`. `test:slow` is `vitest --mode slow`, which **inverts the same list** into `include`; `SLOW_TEST_FILES` is therefore the single source of truth for both tiers (it used to be duplicated into the npm script, where a one-sided edit silently left a file in both tiers or neither). Also available: `npm run test:changed`, `npx vitest related --run <src file>`, or a single file + `-t "<case>"`. The tiers partition the unit suite exactly — fast is every unit file the slow list does not name, so the two always sum to it whatever the counts are. Note the slow tier still flakes under its own fan-out (`dashboard/CutoverEngine.test.ts`) and **lowering `maxWorkers` is a measured non-fix** — see [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md) before trying it — see [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md) → "Two tiers: inner loop vs gate" for the profile and how to re-derive it. Caveat: `--changed` implies `passWithNoTests`, so it exits **0** when nothing matched — check the file count before reading that as a pass.

Per-workspace variants exist for every script: `npm run build:cli`, `npm run test:vscode`, `npm run typecheck:cli`, etc. The three plugins have build variants only (`npm run build:claude-plugin`, `npm run build:codex-plugin`, `npm run build:cursor-plugin`) — they carry no tests or typecheck of their own; what covers them lives in the CLI suite (`CodexPluginManifest.test.ts`, `CodexPluginSkills.test.ts`, `CursorPluginManifest.test.ts`, `CursorPluginSkills.test.ts`) plus each build script's own entry-point assertion.

## Architecture you can't infer from one file

### Two-layer hook model

The product is built on a hook pipeline that runs in the user's project, not in this repo:

1. **AI agent hooks.** `SessionStartHook` and Gemini's `AfterAgent` record session metadata to `<projectDir>/.jolli/jollimemory/sessions.json`; Claude's `StopHook` also reads the transcript (scans plans/references/skills, `async: true`). Hermes has an `on_session_end` hook (below). The other eleven sources have **no hook** (Codex, OpenCode, Cursor Composer, Cursor CLI, Copilot CLI, Copilot Chat, Cline, Cline CLI, Devin, Antigravity, Kimi) — each has a per-source session discoverer + transcript reader under `cli/src/core/` running at post-commit time, with detection either a separate `*Detector.ts` or colocated in the discoverer. None call the LLM. Storage shapes vary widely (Devin/Hermes keep everything in one global WAL SQLite walked as a forest / linear log; Antigravity's per-conversation DB is encrypted and read only for the workspace path, content coming from a sibling plaintext JSONL; the OpenCode/Cursor/Copilot/Devin/Antigravity readers lazy-import `node:sqlite` so an older runtime tolerates the missing module). References + skills extraction is source-agnostic through the shared envelope layer (`TranscriptEnvelopeParser`, `McpBusinessNormalize`, `referencesFromNormalizedResults`): `BUILTIN_DEFINITIONS` holds fifteen reference sources, of which Codex resolves eleven (`match.codex`) and Kimi/Hermes reuse `registry.match("claude", …)` for the seven generic-`mcp__<server>__` definitions — the eight `mcp__claude_ai_*__` first-party connectors are a **known gap** those hosts cannot structurally produce. Kimi and Hermes skills are **observed** (a real `Skill`/`skill_view` tool call), not heuristic. **Full per-source catalogue (exact paths, wire formats, the forest/linear walks, the Kimi/Hermes MCP-prefix gaps, `daemonRescan`): [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md).**

Hermes' `on_session_end` shell hook rides the same `run-hook` dispatch. [`HermesStopHook`](cli/src/hooks/HermesStopHook.ts) mirrors [`CursorStopHook`](cli/src/hooks/CursorStopHook.ts) (does what Claude's Stop hook does — `saveSession`, `recordSessionFromHook`, a detached discovery worker — with no extraction logic of its own) and obeys the shell-hook contract: nothing on stdout (Hermes parses it as JSON), fail open silently, opt-in on `isGitHookInstalled`, basename entry guard. Registration is ONE op: `hermesRegistrar` upserts BOTH the `mcp_servers` and `hooks:` blocks into `config.yaml` via [`HermesConfigWriter`](cli/src/install/mcp/HermesConfigWriter.ts) (byte-identical no-op, atomic write, 0600 preserved through the rename) AND pre-records the `(event, command)` pair in `<HERMES_HOME>/shell-hooks-allowlist.json`, because Hermes silently refuses a hook on a non-TTY start otherwise (`hooks_auto_accept:true` was rejected as a user-only policy decision). POSIX-only for the hook; MCP written on both platforms.

2. **Git hooks** drive a unified queue under `.jolli/jollimemory/git-op-queue/`. `post-commit` enqueues + spawns a detached `QueueWorker` in <5 ms; when the commit comes from an interactive context (a TTY or an AI-agent session — `CLAUDECODE`/`AI_AGENT`/`CURSOR_TRACE_ID`/`GEMINI_CLI`/`OPENCODE`), it then tails the worker's `capture-progress/<hash>.ndjson` stream and prints milestones inline, blocking until the worker emits a terminal event, the watch times out (15 s agent ceiling / 90 s TTY), or the worker is detected dead via its per-hash PID lock (`capture-progress/<sha256>.lock`, written by `acquireCaptureLock` in the worker, probed by `isCaptureWorkerDead` in the watcher). GUI git clients set none of these markers and keep the original fast, silent, non-blocking behavior. The worker holds a 5-min file lock, drains entries in timestamp order, runs the LLM where needed, and chain-spawns a successor if new entries appear after it finishes. Squash entries (and rebase-squash) now go through the LLM-driven `generateSquashConsolidation` pipeline (`cli/src/hooks/QueueWorker.ts runSquashPipeline`) — the old "skip LLM, mechanical merge only" behavior is now the **fallback** when the consolidation call fails. Rebase-pick entries skip the LLM and just migrate hashes 1:1. `prepare-commit-msg` writes `squash-pending.json` so the worker recognizes squash before picking a consolidation strategy. See [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md) for the queue rationale (each op gets its own file precisely because the previous single-slot pending files lost summaries during rapid amend/rebase sequences).

### Push channel: one watch list, two hosts, a growing set of kinds

JVM hosts can't notice a write in-process, so the CLI pushes `refresh` notifications. [`computeWatchTargets`](cli/src/daemon/DaemonServer.ts) is the single watch list, armed by both `jolli daemon` and `jolli ide-bridge-serve` (the latter is what runs today; `DaemonNotificationClient` is now just the plugin-wide listener registry, fed by `injectRefresh`), both building the payload via `buildRefreshParams` — add a target in one place, never a second list. Read the kinds off `RefreshKind`, not a count (`memory-db` is newest; `memory-bank` is declared but never emitted). Full rationale: [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md).

- **`queue`/`orphan-ref`/`memory-db`/`memory-bank` are commit-time; `working-context`/`claude-plans` are mid-session.** Only the first group changes installation state and reaches IntelliJ's `refreshStatus()`; the context kinds take `refreshWorkingContext()`. An **unknown** kind must fall through to the status path (a new kind is a compatible extension; heavier-than-necessary is the safe way to be wrong).
- **IntelliJ has two listener lists and which a panel joins is a real decision.** `addStatusListener` (~15 wide, each re-runs an expensive query) vs the narrow `addWorkingContextListener` (two: CONTEXT list + Working Memory). A panel may be on both (`PlansPanel`, because it also gates on `status.enabled`) — not a double-refresh, since each fires only its own list. `PinnedPanel` is on **neither** (renders from `pins.json`). Putting a commit panel on the narrow list, or a context panel on only the status list, silently un-does this.
- **Both debounces ESCALATE, never overwrite** (shared [`RefreshEscalator`](intellij/src/main/kotlin/ai/jolli/jollimemory/core/RefreshEscalator.kt) `AtomicBoolean`): last-writer-wins would drop the status refresh when an agent emits `orphan-ref` then `working-context` moments later, so the just-created memory never appears. One-way on purpose.
- **`claude-plans` is the one kind carrying a payload** (`params.names`) — `~/.claude/plans/` is machine-global, so only the OS create event knows "what's new"; slug/existence/project-affinity decisions stay in `plans-register-new`, attribution is `isPlanFromCurrentProject`'s job.
- **Both context targets are filename-gated** (`.jolli/jollimemory/` also holds the many-times-a-second `debug.log`); `fs.watch` may omit the filename, and then `DaemonWatcher` stays silent rather than firing blind — IntelliJ's own VFS watcher on `plans.json` is the kept fallback. One signal bypasses this channel entirely: a markdown note's in-place edit reorders the CONTEXT list via mtime with no `plans.json` write (VS Code catches it via `onDidSaveTextDocument`, IntelliJ via `.md` VFS writes matched against `detectNotes`).
- The kind strings are a cross-language contract (`RefreshKind` / `RefreshKinds.kt`, pinned by `DaemonNotificationClientTest`); a rename not mirrored fails silently. `DAEMON_PROTOCOL` does NOT bump for a new kind (a bump disconnects old clients — worse than falling through to the status path).

### Storage: orphan branch + pluggable `StorageProvider` + two `.jolli/jollimemory/` dirs

Summaries live on the git orphan branch `jollimemory/summaries/v3` in the user's repo and are written via plumbing only — the branch is **never checked out**. Read with `git show <branch>:<path>`; write with `hash-object` + `mktree` + `commit-tree` + `update-ref`.

The orphan branch I/O is wrapped behind a `StorageProvider` interface (`cli/src/core/StorageProvider.ts`). Three backends ship today, picked by `StorageFactory` and swapped in at runtime via `setActiveStorage()` in `SummaryStore.ts`:

- `OrphanBranchStorage` — orphan-branch-only, the legacy mode (the only mode in 0.98.0 and earlier).
- `FolderStorage` — folder-only.
- `DualWriteStorage` — **the default** (the `storageMode` config key is RETIRED: `StorageFactory.createStorage` ignores a residual value with a log line and routes by the four-state cutover table instead — `uncutover` → dual-write as before, `legacy-fenced`/`cutover` → `SqliteStorage`, `blocked` → throw; see `cli/src/dashboard/CutoverRouter.ts`). Writes go to both the orphan branch (system of record) and the Memory Bank folder. `<localFolder>` is the user's `localFolder` config — one Memory Bank root can host multiple repos, each in its own `<repo>/` subfolder. The folder has two layers (FolderStorage docstring is the source of truth):
  - Hidden `<localFolder>/<repo>/.jolli/` — canonical JSON for programmatic access: `summaries/<commitHash>.json`, `transcripts/<commitHash>.json`, `plans/...`, `notes/...`, `index.json`, `shadow-status.json`.
  - Visible `<localFolder>/<repo>/<branch>/...` — human-browsable Markdown auto-generated from the JSON: `<slug>-<hash8>.md` for summaries, `plan--<slug>.md` for plans, plus visible note copies. The slug is derived from the commit message via `FolderStorage.slugify()`.

  Reads come from the orphan branch (the visible Markdown layer is generated, never read back).

  **Code-side note:** the `kbRoot` variable in `KBPathResolver` / `FolderStorage` is the return value of `resolveKBPath(repoName, remoteUrl, customPath)` — already concatenated to `<localFolder>/<repoName>`, i.e. **already includes** the `<repo>` segment. So in code, `kbRoot` = per-repo path; in user-facing docs the path is written `<localFolder>/<repo>/...`. Same disk location, different naming layers. The `KB`-prefixed module names (`KBPathResolver`, `KBTypes`) and the `kbRoot` variable are legacy identifiers from when the feature was internally called "Knowledge Base"; the user-facing label is "Memory Bank".

The VS Code extension's `activate()` (and the IntelliJ plugin's equivalent) checks `MetadataManager.readMigrationState()` on every start: if the orphan branch has data but migration has not completed (fresh install, or the user wiped the folder), `MigrationEngine.runMigration()` runs automatically. There is no opt-in — Memory Bank is on by default. The Settings → **Memory Bank** tab is the user-facing entry point for re-targeting the folder; clicking **Migrate to Memory Bank** re-runs migration into a fresh `-N`-suffixed folder and archives the previous folder's repo identity (content files are untouched).

Display and write paths in `SummaryStore.ts` / `LocalSearchProvider.ts` go through the active provider, so adding a fourth backend (e.g. SQLite, S3) is a single new class plus a factory wiring change. Existing code that hard-coded git plumbing is gone — don't reintroduce it.

Local non-summary state is split across **two** `.jolli/jollimemory/` directories — don't conflate them:

- `~/.jolli/jollimemory/` — **machine-global**: `config.json` (authToken / apiKey), `dist-paths/` (per-source dist-path indirection), `run-hook` / `run-cli` / `resolve-dist-path` hook entry scripts. Resolved by `getGlobalConfigDir()`.
- `<projectDir>/.jolli/jollimemory/` — **per-project, gitignored**: `sessions.json`, `cursors.json`, `git-op-queue/`, `notes/`, `plans.json`, `briefing-cache.json`, `space-binding.json` (cached repo→Space binding, 7 d TTL), `debug.log`. Resolved by `getJolliMemoryDir(cwd)` ([`Logger.ts`](cli/src/Logger.ts)). `profile.json` is the exception — **repo-wide, not per-worktree** (anchored to the main worktree via `git rev-parse --git-common-dir`, [`RepoProfile`](cli/src/core/RepoProfile.ts)) — holding `backfillDismissed`, the cutover throttles, `cutoverFence`, and the `manuallyDisabled` switch. When `manuallyDisabled` is set EVERYTHING about that repo stops (orphan + SQLite writes, hooks, plugin bootstraps, skill refresh, the machine-wide sweep); `cutoverFence` (`{reason, at}`) freezes only the orphan branch (new runtimes keep writing SQLite / reading the DB, and `jolli enable` must NOT clear it — only doctor's manual path may).

  Two disable-related rules are review blockers, both because pre-0.99.11 builds read the old field shapes: **folding `cutoverFence` into `manuallyDisabled` is a review blocker** (a shipped plugin runs `uninstall()` from its SessionStart bootstrap on seeing the switch — measured wiping shared hooks / Gemini hook / `.mcp.json` / `.cursor/mcp.json` across every worktree once per session; `probeCutoverDrift` is the compensating control), and **`userDisabled`'s read branch must not be deleted** (retired as the write field, it still WINS in both `readManualDisableFlag` and `readManualDisableFlagSync`; the reader folds it onto `manuallyDisabled` and drops the key, since a fence-poisoned `manuallyDisabled:true` never appears without a trustworthy `userDisabled:false` beside it). Full saga: [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md).

  - The dashboard registry (`dashboard-repos.json`) stores **no** disable state — adding a second record of it is a review blocker. Disabled-ness derives from the profile via `isRepoDisabled` (`existingWorktrees(repo).every(readManualDisableFlagSync)` — `every` not `some`, and the SYNC reader). Removal (`forgetRepo` / [`RepoForget.ts`](cli/src/dashboard/RepoForget.ts)) addresses by IDENTITY and is a different question; `dbBackfillRepos` receives the WHOLE roster and is the only writer of `repos.disabled_at`.
  - **Per-source toggles (`claudeEnabled`/`cursorEnabled`/…) are a second, independent axis** through `isSourceEnabled` ([`SessionTracker.ts`](cli/src/core/SessionTracker.ts)) — grouped (`cursor`+`cursor-cli`, `copilot`+`copilot-chat`, `cline`+`cline-cli`), anything but explicit `false` is on. Every tier that reads an agent's store must honour them: `readSourceGate` ([`DbBackfill.ts`](cli/src/dashboard/DbBackfill.ts)) resolves the config once per pass and narrows both `dbBackfillRepos` and `collectSessionEvents` (narrowing only the machine-wide scan is worse than nothing — absence from `preScanned` triggers the per-repo fallback). Filter on the predicate, not `SESSION_SOURCES` membership (`gemini` has no entry); nothing is retroactive; an unreadable config reads ENABLED for all.
  - "EVERYTHING stops" is scoped to writes about THAT repo — `jolli dashboard` still opens from a disabled repo (a machine-level view of every registered repo). `executeDashboard` skips only the `cwd`-aimed `registerRepo`, never the machine-scoped `ensureDashboardDbExists` / `opportunisticSnapshot` / roster sweep; the gate reads `readManualDisableFlagSync` (read-only — must not persist a profile decision on the way to a page).
  - **Auto-cutover's foreground trigger sweeps the WHOLE roster** (`autoCutoverAllRepos`, [`AutoCutover.ts`](cli/src/dashboard/AutoCutover.ts)) — `jolli enable`, bare `jolli`, `jolli dashboard` all call it; only `QueueWorker`'s `maybeAutoCutover(cwd, {throttle:true})` stays per-repo (it runs on every commit). The sweep reads the whole registry, asks `hasLiveWorktree` first, decides disabled-ness with `isRepoDisabled` (never a hand-rolled `readManualDisableFlagSync(root)`), and takes no `configDir`; `AutoCutoverSweepOptions` has no `throttle` field, a type guarantee that no foreground caller throttles.
  - **What bounds a repo that can never cut over is a MEMO, not a window** — turning it back into a window or a failure-count is a review blocker. [`CutoverBlock.ts`](cli/src/dashboard/CutoverBlock.ts) records the refusal code + a **witness** (every source's pinned tip + `__CLI_PKG_VERSION__`); `readCutoverBlock` answers "blocked" only while the witness is unchanged. Only the two IMPORT refusals get a code (`no-summary-rows`, `stored-nothing`); `runCutover` clears before step 1, writes only at those two, and never consults it (`jolli cutover` bypasses every gate); anything unreadable = NO block.

### How to add a dashboard migration

The rules are in the critical-rules section above; this is the procedure.

1. **Name it with a UTC timestamp**: `date -u +%Y-%m-%d-%H%M` → `2026-08-19-1430-prune-orphan-events`. The timestamp buys uniqueness and a chronology a human can read; **it is not a sort key** — array order is the execution order, and only appending is allowed. The first twelve entries keep their original `<CONSTANT>_DDL` names (frozen, they predate this convention); everything after them is timestamped, which `MigrationFingerprints.test.ts` enforces — the legacy names must stay a contiguous PREFIX, so a timestamped entry always appends past all of them even when it heals one of them.

2. **Append it to `MIGRATIONS`** in [`DashboardDb.ts`](cli/src/dashboard/DashboardDb.ts) — never insert into the middle. Every entry is inline in that array today. A one-file-per-migration layout (the web backend's `dao/migrations/` shape) was built and reverted: its only subject was the heal entry that got removed, and the seam it needed — a leaf module for `sqlMigration` / `addColumnIfMissing`, since an entry in its own file is imported BY `DashboardDb.ts` and would otherwise close a cycle — is worth re-adding only alongside a real entry that wants it.

   ```ts
   // Pure SQL — gets a fingerprint and drift-warning for free.
   sqlMigration("2026-08-19-1430-prune-orphan-events", "CREATE TABLE IF NOT EXISTS foo(…) STRICT;")

   // Needs to inspect the schema (any add-column step does) — a code entry.
   { name: "2026-08-19-1430-…", run: (db) => addColumnIfMissing(db, "commits", "foo", "TEXT") }
   ```

   Reach for `sqlMigration` unless an add-column step forces the other form: only entries carrying `sql` can be fingerprinted, and a code entry costs you a companion test instead.

3. **Make it survive being run twice** — `IF NOT EXISTS`, `OR IGNORE`, a self-excluding `WHERE`, `addColumnIfMissing`. `run(db)` may inspect the schema and branch, but must NOT derive business data (read other tables, compute in TypeScript, write the result back).

4. **Let any writable open apply it.** Migration is not tied to a command: `withDashboardDb` is the only entry point that migrates, and a commit, a recall, an IDE tick or a dashboard page load all reach it. By hand, `npm run cli -- dashboard` is the shortest path; `jolli doctor --schema-log` then shows the entry.

5. **Add its guard.** A `sql` entry needs its fingerprint in `MigrationFingerprints.test.ts` (`npm run test -w @jolli.ai/cli -- src/dashboard/MigrationFingerprints.test.ts` prints what it should be). A code entry needs a companion test asserting every object it creates — the fingerprint test fails until one exists, and it requires that test **beside the entry**: a sibling `migrations/<name>.test.ts` for an entry in its own file, `DashboardDb.test.ts` for one still inline. The two locations are not interchangeable, or a split entry passes on a comment in the big file that happens to mention it.

6. **Regenerate the schema snapshot, and read its diff.** [`cli/src/dashboard/schema.snapshot.txt`](cli/src/dashboard/schema.snapshot.txt) is the checked-in description of what the whole list builds, and the ONLY guard that looks at the RESULT rather than the mechanism — the fingerprints pin an entry's bytes, and the re-runnable test compares a database to itself, so an entry that creates the wrong object passes both. It is also the only place the CURRENT shape of the database is written down: the DDL constants are frozen at the shape they shipped with, so the six columns `ALTER`ed onto `session_tool_use` appear in no `CREATE` statement anywhere in the source.

   ```bash
   JOLLI_UPDATE_SCHEMA_SNAPSHOT=1 npx vitest run src/dashboard/SchemaSnapshot.test.ts   # from cli/
   ```

   The diff is the review artifact — a migration PR that regenerates it without the diff appearing in the review has skipped the guard. Deliberately an env var rather than vitest's `-u`, which is one keystroke away from rubber-stamping a schema change nobody looked at. **This step is not only for a new entry**: the live DDL constants that the code entries are assembled from (`STATS_DAILY_TABLE_DDL`, `SYNC_STAMP_ZERO_BACKFILL_DDL`, …) carry no fingerprint, because their entries carry no `sql` — editing one changes every fresh install's schema, and this snapshot is the only thing that notices.

**Changing something already committed** — you cannot; ship a new entry:

| Want | Do |
|---|---|
| Add a forgotten object | New entry that asserts it re-runnably |
| Fix a column's type | New entry using SQLite's table-rebuild dance; the old entry stays untouched |
| Bring stale RELEASED databases up to date | New entry that re-asserts what the old one should have created, with its OWN body — never by pointing a second name at the first entry's function (two entries sharing a body is a test failure). First check the entry you are repairing has actually shipped: if it has not, no user database carries the name, and the only machines involved are developers' own |
| Delete a bad entry | Never. Every database that ran it would read it as never applied and run it again |

### VS Code extension bundles the CLI

`vscode/esbuild.config.mjs` emits two CJS bundles in `dist/`: `Extension.js` (`vscode` external) and `Cli.js` + each hook script, both inlining `cli/src/**`. Consequences: cross-package imports like `../../../cli/src/core/JolliApiUtils.js` resolve at bundle time (don't "clean up" into a package import); `import.meta.url` in `Installer.ts` is esbuild-replaced with a real `__filename`; core is ESM, the extension host is CJS (esbuild bridges).

- **A module's "am I the entry point?" guard must check the entry file's BASENAME, not compare paths** — the `import.meta.url` rewrite points every inlined module at the bundle (= `argv[1]`), so a path comparison is true for every module and any self-running one executes as a side effect of import. Shipped twice (`SessionStartHook`'s `main()` ran inside plugin bootstraps, writing plaintext ahead of the JSON Codex rejects). Unit tests can't see it (no bundle; `VITEST` short-circuits the guard), so five modules' guards are pinned by a source-shape test: `QueueWorker`, `SessionStartHook`, `CodexPluginBootstrapHook`, `CursorPluginBootstrapHook`, `McpLauncher`.

**Hook installation uses dist-path indirection.** Repo hooks are source-neutral — they call `"$HOME/.jolli/jollimemory/run-hook" <type>` ([`HookSettingsHelper.ts`](cli/src/install/HookSettingsHelper.ts)), which delegates to `resolve-dist-path`: it enumerates `~/.jolli/jollimemory/dist-paths/<source>` (two lines each, `<version>\n<path>`) and picks the highest version. Every surface writes its own entry, so **version comparison across surfaces picks the winner, not install order.** At a tie the winner is `SOURCE_PREFERENCE_ORDER` (`["cli","vscode","cursor"]`); `claude-plugin`/`codex-plugin` are deliberately outside it (win only by strictly-higher version). `JOLLI_DIST_PREFER_SOURCE` exists but no shipped surface sets it — don't bake it into Git/Agent hooks, and don't restore direct manifest business hooks (the manifest registers only the bootstrap hook, which installs the canonical Stop/SessionStart via `run-hook`). `traverseDistPaths` **sorts** `readdir` so the TS resolver and the globbing shell `resolve-dist-path` can't disagree — a determinism guarantee; never make behavior depend on WHICH bundle wins.

- **Node resolution is PATH-first with a recorded-runtime fallback**: when the git process PATH has no `node` (GUI git clients launch git with a minimal PATH), the dispatchers fall back to `~/.jolli/jollimemory/node-path` (plain text, the runtime IntelliJ's `NodeRuntime` verified, written/deleted with `node-info.json`). It only `-x`-checks the path, never spawns `node --version` (`prepare-commit-msg` is on the blocking commit path). Changing [`DispatchScripts.ts`](cli/src/install/DispatchScripts.ts): keep PATH-first order and the silent-exit policy (hooks never block git).

### MCP server registration (multi-host)

`jolli enable` wires the `jolli mcp` stdio server into every detected AI host. Registration is handled by per-host `McpHostRegistrar` implementations under [`cli/src/install/mcp/HostRegistrars.ts`](cli/src/install/mcp/HostRegistrars.ts). Each registrar carries a `scope`: **repo**-scoped hosts (config inside the worktree) are registered per-worktree via `registerRepoMcpHosts`; **global**-scoped hosts (one machine-wide file shared by every repo) are registered once via `registerGlobalMcpHosts`. Uninstall calls `removeRepoMcpHosts` — global entries are deliberately **not** removed, since a single-repo uninstall must not break MCP for other repos still using Jolli. Twelve hosts are supported:

| Host | Scope | Config path | Writer |
|------|-------|-------------|--------|
| Claude Code | repo | `.mcp.json` in the project root | `registerMcpInClaude` (custom merge — preserves other servers) |
| Cursor | repo | `.cursor/mcp.json` in the project root | `JsonMcpWriter` |
| Gemini | global | `~/.gemini/settings.json` | `JsonMcpWriter` |
| Codex | global | `~/.codex/config.toml` | `CodexTomlWriter` (hand-written TOML — no external TOML lib) |
| OpenCode | global | `~/.config/opencode/opencode.json` | `JsonMcpWriter` (key `mcp`; entry needs `type:"local"` + combined command array) |
| GitHub Copilot CLI | global | `~/.copilot/mcp-config.json` | `JsonMcpWriter` |
| VS Code Copilot Chat | global | `<vscodeUserDataDir>/User/mcp.json` | `JsonMcpWriter` (key `servers`; entry `type:"stdio"`) |
| Cline (VS Code ext) | global | `settings/cline_mcp_settings.json` under the ext's globalStorage, **per hosting flavor** | `JsonMcpWriter` (default key; Cline CLI has no MCP config) |
| Devin CLI | global | `~/.config/devin/config.json` | `JsonMcpWriter` (default key; entry adds `transport:"stdio"`) |
| Antigravity | global | `~/.gemini/config/mcp_config.json` | `JsonMcpWriter` (default key; stdio inferred from `command`, no type/transport) |
| Kimi Code CLI | global | `~/.kimi-code/mcp.json` | `JsonMcpWriter` (default key `mcpServers`; stdio `{command,args}` — MCP lives in `mcp.json`, NOT `config.toml`) |
| Hermes Agent | global | `<HERMES_HOME>/config.yaml` | `HermesConfigWriter` (hand-written YAML — a single call upserts BOTH `mcp_servers.jollimemory` AND `hooks.on_session_end`, and pre-records the shell-hook approval in `<HERMES_HOME>/shell-hooks-allowlist.json`; POSIX-only for the hook, MCP written on both platforms) |

Each non-Claude registrar is gated on its host's **presence on disk** — deliberately NOT the readability-gated detector that governs discovery / status / toggles, so on a runtime without `node:sqlite` a host reports absent for discovery while MCP is still written. Cline is the one host whose MCP gate is *narrower* than its discovery gate (only the editor extension registers; the CLI ships no MCP config) — do not collapse the two predicates. Each host's per-entry envelope differs (OpenCode `type:"local"`+array, Copilot Chat `type:"stdio"`, Devin `transport:"stdio"`, Antigravity none), each verified against the host's real on-disk config — a shape correct for one silently no-ops on another. **Claude is the exception**: `detected` mirrors `config.claudeEnabled !== false`, but MCP registration runs regardless of `claudeEnabled` (before the hook gate). IntelliJ drives the bundled CLI's enable as a subprocess and has no registry writer of its own. Uninstall removes only the two repo-scoped registries; the nine global entries are deliberately left behind.

**`--repo-hooks-only` skips MCP for every host except Codex, and only when the acting host is Codex** (`pluginBootstrapHost(sourceTag) === "codex"`). That global `~/.codex/config.toml` entry is the ONLY way the Codex plugin gets a working MCP server: a plugin `.mcp.json` can't have one — Codex resolves a relative `cwd:"."` against the plugin root, and every tool derives its repo from cwd, so a plugin-launched server answers empty-but-successful for the bundle dir and nothing recovers the workspace (no `roots`, a 7-var env allowlist). So the Codex plugin ships **no** `.mcp.json` and this bootstrap registers Codex only. Do not restore a plugin MCP manifest or widen the exception.

**`startMcpServer` guards three kinds of cwd — two by refusing to start, the third by withholding tools.** Outside a repository nothing FAILS (storage answers empty-but-successful, which the cutover rule names as worse than no data). A local-agent-child cwd and a plugin-bundle cwd (`**/.codex/plugins/`, `**/.claude/plugins/`, `**/.cursor/plugins/` — [`PluginBundlePaths.ts`](cli/src/core/PluginBundlePaths.ts)) are refused outright. "Not inside a git worktree" is narrower and per-tool: each `TOOL_DEFINITIONS` entry declares a **required** `requiresRepo` (no default, pinned by a partition test), and outside a worktree the `requiresRepo` tools are dropped from `tools/list` while `list_spaces` + every platform tool survive; `createStorage`/`setLogDir` are skipped so no stray `.jolli/` lands in HOME. The bundle check runs FIRST (a marketplace cache is a real checkout). Forced by a measured Cursor failure — it imports Claude plugins wholesale (`.mcp.json` included) and spawns the server before a workspace is known, so the child inherited HOME and served an empty repo with all 32 tools; fixing it by shipping no `.mcp.json` in claude-plugin was declined (it shifts first-session timing for every existing install). Full rationale: [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md).

**The Cursor plugin hits the same trap but needs no exception — `.cursor/mcp.json` is repo-scoped**, so `cursorRegistrar` is already the right writer (via `Installer`'s `pluginHost === "cursor"` `repoHooksOnly` branch, cursor-only, no global host touched). This made `upsertJsonMcpServer` a per-session hot path, so it now (like `upsertCodexMcpServer`) returns before touching anything when the write changes nothing — comparing **content, not bytes** (re-render then compare, so a CRLF/indent-only difference doesn't force a rewrite) — and writes atomically **reading the file's mode back** (`atomicWriteFile` replaces the inode, so a 0600 config would otherwise widen to 0644). Every file these two writers touch is another tool's MCP config (spawn commands + token `env` blocks), so a new atomic writer aimed at a file Jolli does not own is a review blocker without the mode read-back.

### MCP tool set and CLI↔MCP result parity

The `jolli mcp` server exposes ten tools (see `TOOL_DEFINITIONS` in [`cli/src/mcp/McpServer.ts`](cli/src/mcp/McpServer.ts)): four read tools `search`, `recall`, `get_decision_timeline`, `list_branches`; `get_pr_description` (build a PR title + body from the current branch) and `queue_status` (is summary generation still draining — call before `get_pr_description`); `status` (installation & configuration health — the MCP mirror of `jolli status`, wrapping `getStatus()`; reads the site from `config.jolliUrl` and never decodes the API key, so it stays clear of the CodeQL clear-text-logging gate); and three Jolli Space tools `bind_space`, `list_spaces`, `push_memory`. There is no `load_commits` tool. **Every entry declares TWO required booleans, each with its own partition test, and they fail in opposite directions.** `requiresRepo` (nine of ten; `list_spaces` is the exception, since it asks the backend about the *tenant* while `bind_space` / `push_memory` act on *this* repo and branch) decides what is advertised at all — see the `startMcpServer` rule above. `readOnly` (eight of ten; only `bind_space` and `push_memory` mutate) is surfaced as `annotations.readOnlyHint`, the hint a host running an untrusted server gates on: Hermes 0.21.0's `_trust_gate_check` routes every tool WITHOUT `readOnlyHint === true` through an approval prompt and fails closed on missing annotations, so before this existed all ten were gated and a non-interactive `recall` was auto-denied. Neither has a default, so adding a tool without classifying it is a compile error. The risk asymmetry is worth keeping straight: a wrong `requiresRepo: false` is silent and harmful, a *missing* read-only claim is merely pessimistic, and a *false* read-only claim is the dangerous one — it exempts a writing tool from the prompt the operator configured. The public wire shape is `PublicToolDefinition` (`name` / `description` / `inputSchema` / `annotations`) and both built-ins and platform tools are projected onto it, so `requiresRepo` and `readOnly` — like a manifest entry's `binding` / `menu` — never reach a client; a built-in DERIVES its annotations block from `readOnly`, while a platform tool passes through whatever its manifest declared (nothing today), so the backend stays the author of claims about backend tools.

`recall` (MCP) and `jolli recall --format json` (CLI) both call `resolveRecall()` ([`cli/src/core/RecallResolver.ts`](cli/src/core/RecallResolver.ts)), so they return the identical `type`-tagged union (`recall` | `catalog` | `error`), including catalog fuzzy-match on an unrecognized branch.

`search` (MCP) and `jolli search` (CLI) both call `searchHits()` ([`cli/src/core/SearchHits.ts`](cli/src/core/SearchHits.ts)), Orama BM25. Both return `{ hits }` — single-phase. The CLI `search` command's old two-phase catalog / `--hashes` flow was retired; [`LocalSearchProvider.ts`](cli/src/core/LocalSearchProvider.ts) is kept as an unused `SearchProvider` extension point.

The `jolli-recall` and `jolli-search` skill templates (written by [`SkillInstaller.ts`](cli/src/install/SkillInstaller.ts)) prefer the MCP tools (`mcp__jollimemory__recall` / `mcp__jollimemory__search`) and fall back to the CLI here-doc recipe for hosts without MCP support. `jolli-search` is intentionally lightweight (title / snippet / slug / hash; no decisions or recap) — point users to `jolli-recall` for depth.

### `jolli mcp` is a proxy; the server is one daemon per worktree

`jolli mcp` no longer *is* the MCP server. It is a thin proxy ([`McpProxy.ts`](cli/src/mcp/McpProxy.ts)) that ensures a detached per-worktree daemon (`jolli mcp-serve`, hidden — [`McpDaemon.ts`](cli/src/mcp/McpDaemon.ts)) exists and then forwards **raw bytes** between its stdio and a unix socket / Windows named pipe. Nothing host-facing changed: all eleven registrars still write a plain stdio entry, so the per-host envelope divergence documented above is untouched.

Why: every AI session spawned its own server, each re-running `createStorage` and re-reading the summary store. Measured on a real dogfooding machine — **43 `Cli.js mcp` processes**, ~100 MB *steady-state physical footprint* each (`vmmap -summary`, NOT RSS: RSS counts ~22 MB of shared node-binary pages per process and made the waste look 5x smaller than it was). A proxy peaks at ~16 MB, so that ~100 MB steady state is now paid once per worktree instead of once per session.

**Two numbers circulate for the same process and they are NOT the same measurement** — quote which one you mean. Re-measured on the built dist: a live `mcp-serve` daemon sits at **91-103 MB current** footprint but **214-235 MB peak**, because `main()` (plugin loader + update check + stale-skill refresh) and the runtime build are transient. So the ~100 MB in the paragraph above is a steady-state figure, while the ~200 MB in `Cli.ts`'s fast-path comment is a launch-peak figure — never quote either without saying which. The daemon still pays BOTH, once per worktree, and deliberately: it is the process that runs the tools, so it needs the full stack, and giving it a fast path of its own would shave the peak while leaving the steady state — worth little against the 43x the proxy saves. A proxy peaks at 16.8 MB, so what the fast path removes is mostly that transient, multiplied by every open session.

- **The singleton key is the WORKTREE root, not the repo** — siblings share an orphan branch, but `dispatchTool` closes over cwd and five of ten tools are branch-scoped, so collapsing them answers for the wrong branch silently. The socket path is a HASH of the normalised worktree root ([`McpDaemonProtocol.ts`](cli/src/mcp/McpDaemonProtocol.ts)): a real path blows the 104-byte `sun_path` cap, and normalising first stops a case-insensitive FS handing one worktree two daemons.
- **On Windows the address carries a GENERATION suffix**, because a named pipe (unlike a unix socket) cannot be handed over while a client is attached: a retiring daemon answers `retire-deferred` and keeps listening while the proxy relocates the successor to the next generation. `nextScanAction` probes EVERY generation before spawning and takes the LOWEST free one; generation 0 is spelled exactly as before generations existed. `waitUntilUnreachable` is NOT evidence an address can be bound (connect≠bind on Windows) — that is how the pre-fix upgrade stall shipped.
- **The dist version travels in the handshake, never the socket path** (baking it in would split the double-registration case). The daemon greets with `__CLI_PKG_VERSION__` (the CORE version, never a surface's `__PKG_VERSION__`); a strictly-newer proxy answers `retire`, a **tie attaches** so same-version sessions share.
- **Every path that cannot reach a daemon ends in `startMcpServer`** (the pre-existing single-process behaviour) — the three proxy refusals, an unsafe socket dir, an unparseable/foreign peer, a `hello.cwd` hash collision, `retire-deferred`, an exhausted scan. `JOLLI_MCP_NO_DAEMON=1` skips the proxy. The two cwd refusals (local-agent child, plugin bundle) get NO server at all — the intended signal, so the proxy does not restate their stderr.
- **Nothing binds until every cwd guard has run**; `prepareMcpRuntime` builds the whole runtime first (where the two SHARED guards `isLocalAgentChild`/`isPluginBundleCwd` live). The third guard (`isWorktreeRoot === false`) is the proxy's ALONE and its stderr line is written first; other refusal text stays owned by `startMcpServer`. stderr, never stdout (a stray stdout byte desyncs the JSON-RPC framing).
- **Two import graphs are load-bearing** (pinned by source-shape tests): `Cli.ts` reaches `Api.js`/telemetry by `await import` and `McpProxy.ts` stays leaf-only, reaching `startMcpServer` dynamically — a static import silently restores a 62 MB steady state. `unref()` is correct in the daemon (the socket holds the loop) and fatal in the proxy (the retry timer is its only handle). Both ends forward with `pipe()` for backpressure (`{end:false}` on socket→stdout, whose stdout must outlive one connection).
- **The `hello.cwd` assertion must fold exactly what the socket hash folds** (`sameWorktreeRoot`/`normalizePathForCompareOn`, same platform) — a raw `!==` is inconsistent, not stricter, and strands a correctly-routed session as a phantom hash collision. A degraded platform manifest is NOT cached (`McpRuntime.platformDegraded` retries only the platform half).
- **Windows has NO socket-ownership protection** (`isManagedSocketDirSafe` is a no-op there; `\\.\pipe\` is machine-global, first-binder-wins) — a known limitation, not a decision: on a multi-user box another user can squat the pipe and inject tool results into an agent's context. The socket suites are `describe.skipIf(win32)` (a real listener can't bind a filesystem path there and it presents as a HANG, not a red test; CI is ubuntu-only); any `McpDaemonProtocol` case must assert per-platform. Full measured rationale: [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md).

### Site generation lives in a separate plugin package

The `jolli new` / `build` / `dev` / `start` / `convert` / `reverse` / `theme` commands are **not** in this repo. They live in `@jolli.ai/site-cli`, a plugin built and released separately. The host CLI discovers it at runtime through [`PluginLoader`](cli/src/PluginLoader.ts) and [`KnownPlugins.ts`](cli/src/KnownPlugins.ts) (allow-listed by random `jolliPluginId`, never by package name — see the PluginLoader header for the rationale).

When the plugin isn't installed, [`SiteCommandStubs.ts`](cli/src/commands/SiteCommandStubs.ts) is registered as a fallback by `registerMissingStubs(program, loadedPluginIds)` in `Api.ts main()`. The stubs keep the seven Site commands visible in `jolli --help` (grouped under "Jolli Site" by the help formatter) and emit a one-line install hint on invocation. There is no auto-install path — the stub prints `npm install -g @jolli.ai/site-cli` and exits non-zero.

Things to remember when working on plugin-adjacent code in this repo:

- **Adding a new known plugin** = one entry in `KNOWN_PLUGINS` in `KnownPlugins.ts` (id, packageName, installHint, optional `registerStub` callback). PluginLoader derives `KNOWN_PLUGIN_IDS` from this list, so the discovery allowlist updates automatically.
- **A plugin with no stub** is silently absent when missing — the user sees nothing in `--help` for it. Only plugins with a `registerStub` field appear when the package isn't installed. All three shipping plugins currently register stubs: `@jolli.ai/site-cli` ([`SiteCommandStubs.ts`](cli/src/commands/SiteCommandStubs.ts), grouped under "Jolli Site"), `@jolli.ai/space-cli` ([`SpaceCommandStubs.ts`](cli/src/commands/SpaceCommandStubs.ts), grouped under "Jolli Space"), and `@jolli.ai/workflow-cli` ([`WorkflowCommandStubs.ts`](cli/src/commands/WorkflowCommandStubs.ts), grouped under "Jolli Workflows"). The workflow stub is one `workflow` command (subcommands `local-run` / `runs` / `run-status`), not a flat family: `workflow local-run` emits the machine-readable `workflow_cli_required` JSON on stdout (the local-run recipe parses it), while `workflow runs` / `run-status` print the prose install hint and exit non-zero.
- **Don't add `optionalDependencies` for plugins.** The host CLI has zero npm coupling to its plugins. Users `npm install -g` the host and the plugin separately; the plugin declares the host in its own `peerDependencies` (`>=` form, not `^`, so plugins survive host minor bumps).
- **Don't reintroduce `cli/src/site/`.** Anything site-rendering-related belongs in the plugin's repo, not here.
- **Three places consume the plugin's `jolliPluginId`** (host CLI in this repo, the plugin's `package.json`, and the plugin's CI release verification). Renaming an ID is fine — it's an opaque UUID, not a public name — but all three must be updated in lockstep.

### Pushable context kinds are table-driven

Everything a commit summary can push (plans, notes, references, …) is a **`ContextKindDefinition`** in [`cli/src/core/push/`](cli/src/core/push/), registered in one list in [`kinds/index.ts`](cli/src/core/push/kinds/index.ts); `ContextPush.ts` is the generic engine, `ContextKindRegistry.ts` validates + owns field-by-name narrowing. Modelled on `SourceDefinition` / `BUILTIN_DEFINITIONS`.

- **Adding a kind = one definition + one entry in `CONTEXT_KIND_DEFINITIONS`** — nothing in the orchestrators / executor / batch path should need touching (if it does, add the affordance to the generic layer). Registry **order is user-visible** (the per-summary push order).
- **Identity is data; only `title`/`body` are functions.** `field`/`entryKey`/`baseKey`/`recency`/doc-state names are declared as names so the registry can validate them; item-level ones are `ItemField<T>` (a typo is a compile error). Omitting `docIdField`/`docUrlField` gets the uniform `jolliDocId`/`jolliDocUrl` (three legacy kinds override with historical names — a new kind uses the uniform ones).
- **`docType` is a `string` on the wire, not a union.** An unknown tag is `412 doctype_not_allowed` → `DocTypeNotAllowedError`, deliberately NOT in `REPO_WIDE_REFUSAL_NAMES` (it short-circuits one KIND for that summary's push, so one missing config row can't stop the repo pushing anything); on the batch endpoint it's a per-attachment `ok:false` in a 2xx body.
- `assignOwnedAttachments` / `applyPlanUrls` / etc. survive only as legacy adapters — don't extend them for a new kind. **No surface may spell its own `["plan","note","reference"]` list** — it lives once as `LEGACY_NAMED_DOC_TYPES`, expanded by `legacyNamedSelection` / `legacyNamedOwnership` walking the registry (a per-surface copy is what made branch/live-share skip `skill`: a named selection is a COMPLETE answer, so an outdated list is silent). Production passes the map form; the named shapes are test-compat.

### Auth & origin allowlist

`jolliApiKey` (`sk-jol-…`) is a plain or JWT-shaped token whose payload encodes the tenant URL in a base64url-decoded segment. Three places consume it: CLI (`cli/src/core/JolliApiUtils.ts`, canonical `parseJolliApiKey` + `assertJolliOriginAllowed`), VS Code extension (which imports the canonical CLI helpers via the bundled path), and the IntelliJ plugin (Kotlin port). The allowlist is `jolli.ai`, `jolli.dev`, `jollidev.com`, `jollidev.dev`, `jolli.cloud`, `jolli-local.me`, HTTPS-only, with a suffix-boundary check (`host === h || host.endsWith("." + h)`). Validation is **save-time** (OAuth callback, `configure --set`, settings UI, `JOLLI_URL` env at read time) — request paths trust the saved value. Keep the three implementations in lockstep.

**Every path that persists a pasted key must also persist `jolliUrl`**, via `resolveJolliUrlForKey` ([`JolliApiUtils.ts`](cli/src/core/JolliApiUtils.ts)) — four of them today: `configure --set jolliApiKey=…`, the first-run paste in [`GenerationFix.ts`](cli/src/commands/GenerationFix.ts), the VS Code Settings panel, and the `config-save` ide-bridge action (IntelliJ's Settings dialog has its own editable key field, and that action is the JVM host's only config writer). Requests route on the key's own `.u` claim (`resolveAuth` in `JolliMemoryPushClient.ts` never reads `jolliUrl`), so a surface that writes one without the other splits the product in half **silently**: `jolli status`, the MCP `status` tool and the guided front door report `jolliUrl` and never decode the key — deliberately, since a decoded key reaching `console` is what trips CodeQL's `js/clear-text-logging` — while the VS Code and IntelliJ site rows decode the key first and fall back to `jolliUrl`, so they self-correct and the IDE that caused the drift is the one place it cannot be seen. Two shapes are wrong even though they look tidier: writing `jolliUrl: undefined` (both save paths shallow-merge, so that DELETES a URL a legacy key cannot replace — spread it conditionally), and adding a `jolliUrl` field to the Kotlin `JolliMemoryConfig` to fix IntelliJ there (its Gson is `serializeNulls()`, so every unrelated Kotlin save would then transmit `"jolliUrl": null` and blank it on disk — the field's absence is what makes the merge preserve it).

## Project conventions worth knowing

- **Biome** is the formatter and linter (config: [`cli/biome.json`](cli/biome.json)). Tabs, 4-wide, 120 column limit. Rules of note: `noExplicitAny: error`, `noUnusedImports/Variables: error`, `useImportType: warn`. CI runs `biome check --error-on-warnings` — warnings fail.

- **`intellij/` tests run in ONE JVM with JUnit 5 parallel class execution** (`intellij/src/test/resources/junit-platform.properties`, `maxParallelForks = 1`). That is only safe while no test mutates JVM-global state, so one rule is gated by `intellij/scripts/check-global-state.sh` (ratcheting baselines — they may only shrink): (1) production code never touches JVM globals (`System.out/err/in`, `System.getProperty/getenv`, bare `println`) outside `core/HookEnv.kt` — functions that need them take an `env: HookEnv = HookEnv()` parameter; (2) tests never call `System.setProperty/setOut/setErr/setIn`, `mockkStatic`, `mockkObject`, or `mockkConstructor` — build a fake env via `fakeHookEnv(...)` (test sources, `core/TestEnvs.kt`) and pass it in. Legacy offenders carry `@Isolated` until migrated; when you migrate one, drop the annotation and run `check-global-state.sh regen`.

- **Three Gradle gates ride `test`** (see `build.gradle.kts:527`): 
  - `checkGlobalState` — enforces the JVM-global-state rule (see above).
  - `checkNoDirectLlmHttp` (`intellij/scripts/check-no-direct-llm-http.sh`) — all LLM traffic routes through `cli/src/core/LlmClient.ts` — the plugin's own Kotlin LLM stack was deleted, and every model-backed action now spawns `jolli generate`. The gate greps `src/main/**/*.kt` for `api.anthropic.com|java.net.http` against a one-entry `ALLOWLIST` (`core/telemetry/TelemetryFlusher.kt`). Unlike checkGlobalState it has **no baseline** — a hit means fix the code, not record it — and it is **bidirectional**: an allowlist entry that stops matching also fails, forcing the list to shrink in the PR that removed the last use. Do not reintroduce an LLM or HTTP client in Kotlin.
  - `checkActionsDumbAware` (`intellij/scripts/check-actions-dumbaware.sh`) — every action class in `actions/` must declare `DumbAware`. A new action without the marker will fail `./gradlew test` with a hard error and zero compiler warning, so do not assume the IDE will catch it.

- **Use `toForwardSlash` for `\` → `/` path normalization** ([`cli/src/core/PathUtils.ts`](cli/src/core/PathUtils.ts)); never inline `path.replace(/\\/g, "/")` or `path.split(sep).join("/")`. Forward-slash form is the [`StorageProvider.listFiles`](cli/src/core/StorageProvider.ts) contract and the input every downstream regex / prefix consumer expects — one forgotten inline normalization on Windows silently broke webview transcripts in production. The helper does **only** `\` → `/`: if you also need lowercasing or trailing-slash strip, use `normalizePathForCompare` instead. Biome cannot lint this pattern, so the rule is enforced socially — inline reintroduction is a review-blocker. Exempt: code already inside a domain helper that wraps the conversion (`normalizePathForCompare`, `normalizePathForMatch`, `toFileUrl`, `validateRelPath`); tests asserting on a specific separator; regexes whose `\\/g` is matching a literal backslash for non-path reasons.

- **A `Test timed out in NNNNms` failure is a load signal, not a regression.** About a dozen CLI test files spawn real `git` subprocesses on purpose (`cli/src/sync/*`, `cli/src/install/GitExclude`, `cli/src/core/{Locks,KBPathResolver,BranchCommitLister,RepoProfile,PushControl}`), and the vscode suite does real flag-file IO. Under a full run with `--coverage` those get CPU-starved and time out — indistinguishable at a glance from a real break, and a common source of wasted investigation. **Triage by failure shape first:** timeout → re-run that file alone with the stock timeout (green in isolation is the proof it was contention); assertion or thrown error → investigate as a regression. Tune timeouts in `cli/vite.config.ts` / `cli/vitest.acceptance.config.ts` / `vscode/vitest.config.ts` only (all three at 60 s) — a per-file `vi.setConfig({ testTimeout })` *replaces* the global instead of widening it, and a `--testTimeout` flag cannot override such a clamp. Git isolation is monorepo-global in [`test/gitEnv.ts`](test/gitEnv.ts) at the repo root, wired into all three of those configs — env vars, unlike per-invocation `git -c` flags, are also inherited by the git subprocesses that the *production code under test* spawns. Don't re-add a per-file prologue, and read that file's header before adding a git env var (it explains why an author identity must not be injected). Full rationale: [`cli/DEVELOPMENT.md`](cli/DEVELOPMENT.md) → "Real-`git` tests: isolation and load".

- **Never include AI/Claude co-author information in commit messages.** No `Co-Authored-By: Claude …` trailers, no "🤖 Generated with …" footers — for either commits or PR descriptions. The repo is going open-source and history should read as human-authored work; only `Signed-off-by:` is required.

(The DCO sign-off, `npm run all` gate, CLI coverage floor, and worktree-aware requirement are stated as critical rules at the top of this file; they are not repeated here to keep this file as a single source of truth.)

## Release flow

Releases for both **CLI** (`@jolli.ai/cli` on npm, tag prefix `release-cli-v`) and **VS Code extension** (`jolli.jollimemory-vscode` on VS Code Marketplace + Open VSX, tag prefix `release-vscode-v`) follow the same model. Each is triggered by manually running its publish workflow ([`publish-cli.yaml`](.github/workflows/publish-cli.yaml) / [`publish-vscode.yaml`](.github/workflows/publish-vscode.yaml)) with an existing signed tag as input — pushing the tag alone does not publish. Each minor has a long-lived `release/<minor>.x` branch shared by both artifacts; tags must be reachable from such a branch. Step-by-step commands and the full set of CI checks are in [`RELEASE.md`](RELEASE.md). Four things aren't obvious from the workflow files:

- **Hotfixes do not bump main's version for the affected artifact.** When fixing a shipped version while main carries unfinished features, edit `<artifact>/package.json` only on `release/<minor>.x`. Main's `package.json` represents "what main would publish today" for that artifact — it stays at the previous version until main re-enters a shippable state. CLI and VS Code versions are independent, so hotfixing one does not require touching the other.
- **Cherry-picking a hotfix back to main excludes the version-bump commit.** Pick only the fix commit. Picking the `release: <artifact> <version>` bump commit too will drift main's version past what main can actually publish.
- **Tags must be signed via sigstore** (`git tag -s release-<artifact>-v…`, with [`gitsign`](https://github.com/sigstore/gitsign) configured as the git signer — no long-lived key required). Both workflows verify with `gitsign verify` against an allowlist of OIDC identities. This is independent of, and in addition to, the DCO sign-off requirement on commits.
- **VS Code marketplace publishes are idempotent on retry.** `publish-vscode.yaml` checks each marketplace (VS Code, Open VSX) before publishing and **skips** the step if the version is already there. A run that succeeded on one marketplace and failed on the other can be retried with the same tag — the already-published one will be skipped, only the missing one will be attempted.

**The three plugins release differently — no workflow, no tag, no npm.** Each carries its own version in its `plugin.json` and is published by the bash scripts in `<plugin>/scripts/`, which build the bundle, assert the dist/skill/config inventory, `rsync --delete` the tree into a separate marketplace checkout, and commit it there with a DCO sign-off. Progression is `publish-local.sh` → `publish-dev.sh` → `publish-prod.sh`; `publish-zip.sh` produces an offline archive. Two things reverse the CLI's habits. First, `publish-prod.sh` **refuses any version that is not strictly higher** than the last release in that repo when content changed (bump `plugin.json` first — the opposite of a local verdaccio rehearsal, where you republish the same version). Equal-only was not enough: the monorepo once sat at `1.0.0` while prod had published `1.0.1`, so a publish from main would have shipped a silent downgrade that `/plugin update` reads as "up to date". `publish-dev.sh` passes `dev` to `publish_git_repo` and **skips that guard entirely** — a rehearsal republishes one version rather than inflating it, which is how the Claude dev marketplace ran to `1.0.5` past a prod on `1.0.1` and then began refusing real releases; the cost is that testers must remove + re-add rather than update, and a green dev run no longer proves prod will accept the version. Second, because the marketplace repos are public, `publish-prod.sh` is a user-visible release — never run it speculatively.

All three trees also carry **two copies of `LICENSE`** — the tree root (the marketplace repo's root) and `plugins/jolli/` (the unit `/plugin install`, `codex plugin add`, a Cursor install and the desktop zip actually copy) — and both are listed in each `_publish-lib.sh`'s `PUBLISH_REQUIRED_CONFIG`. Do not re-add an `--exclude 'LICENSE'` to `publish_sync`: the mirror is the only thing that puts the Apache-2.0 text in front of users, and the exclusion that used to protect the prod repo's hand-created copy is what left the dev mirror and the zip with no license text at all. The mirror also runs `git -c core.excludesFile=/dev/null` deliberately: a developer's global gitignore matching `SKILL.md` has silently dropped skills from a published plugin before.
