# 52. OAuth Browser Login Flow

## Topic Statement

Sign the user in by opening their default browser to the Jolli login page with a CSRF nonce, listening on a local single-route callback server, and exchanging the returned single-use authorization code for a session token that is then persisted to the per-user config file in one atomic write.

## Scope

**In scope:**

- Generation and lifetime of the per-attempt CSRF nonce.
- Construction of the URL the browser is opened to, including the parameters that select between code-exchange and the legacy fallback.
- The local callback server's lifecycle: where it binds, when it shuts down, what routes it answers, what it returns to the browser tab.
- The two callback shapes the server accepts and how the right one is selected.
- Validation rules applied to the callback (state match, presence of `code` or `token`, presence of `error`).
- The user-facing error messages mapped from the server's `error=<code>` query parameter.
- The single atomic write of credentials at the end of a successful flow.
- Two parallel implementations of this flow: one that listens on a local TCP loopback port (used by the CLI and the JVM IDE plugin), and one that registers a deep-link URI handler with the host IDE (used by the editor extension).
- The silent login-window expiry that bounds how long the JVM IDE plugin's local server holds its port.

**Out of scope (boundaries):**

- The HTTP exchange that trades the authorization code for credentials (covered by **CLI Authorization Code Exchange**).
- The structure and parsing of the returned product API key (covered by **Jolli API Key Format and Parsing**).
- The allowlist that gates which Jolli origin may be used (covered by **Jolli Origin Allowlist Enforcement**).
- The on-disk shape, env-var fallbacks, and masking of the credential file (covered by **Auth Credential Storage**).
- The pre-callback server side: which page the browser lands on, how the user authenticates with their identity provider, how the server mints a single-use code.

## Data Contracts

### CSRF nonce

A per-attempt random value generated by the client immediately before the browser is opened.

| Property                | Value                                                                                                                |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Encoding (canonical)    | 32 random bytes, lowercase hex (64 hex characters).                                                                  |
| Encoding (JVM IDE port) | 16 random bytes, lowercase hex (32 hex characters).                                                                  |
| Source                  | A cryptographically secure random source.                                                                            |
| Transport               | A **top-level `state` query parameter** on the outbound login URL, on all three surfaces. The JVM IDE port's advertised callback address is the bare `http://localhost:<port>/callback` — the nonce is **not** embedded in the callback address. |
| Lifetime                | One sign-in attempt. On the deep-link variant it is held in a mutable field and cleared on the next callback (success or failure) and on certain pre-flight errors; on the two loopback variants it is a per-attempt value that simply dies with the attempt. |
| Storage                 | In-memory only. A reload of the host process during sign-in invalidates the in-flight attempt.                       |
| Purpose                 | Per RFC 6749 §10.12, sent on the outbound login URL and matched against the value echoed back on the `?code=` callback. It is the **only** CSRF protection in this flow — there is no code challenge / verifier exchange anywhere. |

### Outbound login URL

The URL the browser is opened to. Built from the saved Jolli origin plus query parameters:

| Parameter          | Value                                                                                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `cli_callback`     | URL-encoded callback target. Canonical loopback variant: `http://127.0.0.1:<port>/callback`. JVM IDE loopback variant: `http://localhost:<port>/callback`. Deep-link variant: `<scheme>://<extension-id>/auth-callback`. |
| `state`            | The CSRF nonce (top-level on all three surfaces).                                                                                |
| `client`           | A short identifier of the calling surface (`cli`, `vscode`, or `intellij`).                                                       |
| `client_version`   | URL-encoded build version of the calling surface, so the server can apply the same per-surface minimum-version gate at sign-in that it applies to later API calls. The canonical port sends `dev` when the version constant is absent (a development / test run); the JVM IDE port sends the deliberately gate-failing sentinel `0.0.0` when its version resource is missing. |
| `generate_api_key` | `true` only when the flow is asking the server to mint a fresh product API key: no key on disk, **or** the on-disk key's embedded tenant differs from the target Jolli URL (so a cross-tenant switch completes in one sign-in instead of two). Omitted otherwise, so a same-tenant re-auth does not rotate an existing (possibly hand-configured) key. The JVM IDE port additionally forces it to `true` for every **user-initiated** "Sign In" entry point, so a manual recovery from a revoked same-tenant key actually replaces the dead key; its non-interactive re-auth path (the push / create-PR retry) does not force it. |
| `device_name`      | Sanitized host machine name — trimmed, restricted to `A-Za-z0-9 _.-`, truncated to 32 characters, and omitted entirely when the result is empty. Sent **only alongside `generate_api_key=true`**. It scopes the server's per-user idempotency key, so signing in from a second machine mints a **second** key row rather than invalidating the first machine's key. The sanitization deliberately mirrors the server's own, so a sketchy hostname cannot produce a client/server name mismatch. |
| `install_id`       | The anonymous per-machine install identifier (strict lowercase UUID), sent so the backend can write the install→account attribution row when it mints the key. Recorded regardless of `generate_api_key`. Sent by the canonical port and the JVM IDE port; the editor-extension deep-link variant sends **no** `install_id` at all. |

The path component of the login URL is `/login`.

#### Parameter ordering (pinned, and different per surface)

The query order is fixed per surface and deliberately not unified — captures and server logs stay comparable, so one surface must not be "fixed" to match another in isolation:

| Surface            | Order                                                                                                    |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| Canonical (CLI)    | `cli_callback` → `state` → `client` → `client_version` → `install_id` → `generate_api_key` → `device_name` |
| JVM IDE port       | `cli_callback` → `state` → `client` → `client_version` → `generate_api_key` → `device_name` → `install_id` |
| Editor extension   | `cli_callback` → `state` → `client` → `client_version` → `generate_api_key` → `device_name` (no `install_id`) |

The JVM IDE port's login URL is composed by the shared command-line runtime on its behalf (see **Notable Behavior**), which is also where its origin-allowlist check happens.

### Callback shapes

The callback server / handler accepts three mutually exclusive query-string shapes on its single accepted route:

1. **Code-exchange (preferred).** `?code=<single-use-code>&state=<echoed-nonce>`. The code is opaque and single-use; the actual session token never appears in the browser address bar.
2. **Legacy token-in-URL (fallback).** `?token=<token>&jolli_api_key=<key>`. The server delivered credentials directly because the tenant has not yet shipped the code-exchange endpoint. State is not echoed on this path.
3. **Error.** `?error=<code>`. The server failed before it could mint a code or token.

### Accepted route

| Variant                      | Route path       | Match                                                       |
| ---------------------------- | ---------------- | ----------------------------------------------------------- |
| Canonical loopback server    | `/callback`      | **Exact** string equality on the request path.               |
| JVM IDE loopback server      | `/callback`      | **Prefix** match — the route is registered as a context, so `/callback/anything` also reaches the handler. |
| Deep-link URI                | `/auth-callback` | Exact string equality on the URI path.                       |

Any other path on the canonical loopback server returns HTTP `404` with body `Not found`. The JVM IDE loopback server registers only the one context, so a non-matching path is answered by the platform's own default handler; it never reaches the sign-in decision tree. Any other path on the deep-link URI handler is logged and rejected with a discriminated error result.

**No HTTP method validation.** Neither loopback server inspects the request method: a `GET`, `POST`, `HEAD`, or anything else on the callback route is processed identically. The flow relies on the nonce, not the method.

**First request to the route consumes the attempt.** Both loopback servers are single-shot on the route, and neither pre-screens the query string before consuming: the *first* request that reaches the callback route resolves the in-flight attempt. A local process that hits the ephemeral port with a garbage (or empty) query therefore aborts the sign-in — the canonical port surfaces "No authorization code or token received", the JVM IDE port surfaces the same classification through its failure path. Retrying means starting a new sign-in.

### Local callback server

| Property              | Value                                                                                                                                                                |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bind address          | `127.0.0.1` (loopback only) on both loopback variants.                                                                                                                 |
| Bind port             | `0` — the operating system assigns a free ephemeral port; the actual port is read after the bind and used to build the `cli_callback` URL.                              |
| Routes accepted       | One: the accepted route above (exact on the canonical port, prefix on the JVM IDE port).                                                                                |
| Single-use            | The server shuts down after the first callback reaching the route is processed, valid or not.                                                                          |
| Browser-tab response  | **Differs by surface** — the canonical port renders its own styled HTML; the JVM IDE port redirects to a hosted completion page. See "Browser-tab response by surface". |

### Browser-launch behavior

On the canonical port the browser is launched as a **detached** child process so the local process is free to exit independently of the browser, and the login URL is also printed to standard output beforehand so the user can paste it manually if nothing opens. The editor extension and the JVM IDE port instead delegate to the host IDE's own "open in external browser" facility; a failure there is a launch failure surfaced as a UI message (see the timeout / failure rules below).

### Browser-tab response by surface

**Canonical loopback port** — renders its own self-contained HTML page (no external CSS or JS): a styled card with a check-mark or cross-mark icon, a headline, and the message. The success page (status `200`) carries the only inline script: a ~1.5-second timer calling `window.close()` and a ~2-second timer rewriting the hint to "You can close this tab now." All title and message text is HTML-escaped before interpolation.

**JVM IDE loopback port** — does not render sign-in markup at all. It answers with a `302` redirect to a hosted completion page on the configured Jolli origin, so the user lands on the same page the editor-extension flow ends on:

| Outcome                                     | Response                                                                                     |
| ------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Success                                     | `302` to `<jolliUrl>/cli-complete`.                                                          |
| Structured callback failure                 | `302` to `<jolliUrl>/cli-complete?error=<classified code>`.                                   |

Plain-text fallbacks are used **only** when no redirect target could be produced (the shared runtime was unreachable, timed out, or returned a malformed / redirect-less response):

| Condition                                                    | Status | Body                                                          |
| ------------------------------------------------------------ | ------ | ------------------------------------------------------------- |
| Reported success but no redirect target                      | `200`  | `Sign-in complete. You can close this window.`                 |
| Reported failure and no redirect target                      | `500`  | The failure message, or `Sign-in failed. Please try again.`     |
| The callback handler itself threw                            | `500`  | `Sign-in failed: <message>`                                    |
| A second request arrives after the attempt already resolved  | `408`  | `Sign-in has already ended. Please try again.`                  |

The `200` fallback body is deliberately success-worded rather than reusing the failure copy: a version-drifted runtime that omits the redirect target must not leave the browser tab reading "failed" while the IDE has already flipped to signed-in.

### Login-window expiry (JVM IDE port)

The JVM IDE plugin schedules a one-shot expiry **5 minutes** after the local server starts. Expiry is **silent**: it closes the server to release the TCP port and fires **no** error callback and **no** notification. It is not a user-visible outcome — every user-visible outcome comes from a real callback (success or structured failure) or from a real launch failure (port bind failure, browser-launch throw, off-allowlist tenant URL, shared runtime unreachable). The user simply clicks Sign In again whenever they come back.

The canonical loopback server and the editor-extension deep-link handler impose no login-window expiry of their own. (The editor extension does hold a short deferred expiry on its *nonce* — not on a listener — for the case where the host's external-URI consent dialog reports "not opened".)

### Server-error code mapping

When the callback carries `?error=<code>`, the handler maps the code to a user-facing message. The full table — the one the JVM IDE port uses, via the shared runtime — is:

| `error` code             | User-facing message                                                                          |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| `access_denied`          | Access was denied. Please try again.                                                          |
| `auth_fetch_failed`      | Failed to fetch user information from the authentication provider.                            |
| `failed_to_get_token`    | We couldn't retrieve your credentials. Please try signing in again.                            |
| `invalid_callback`       | The sign-in callback was rejected by the server. Please try again.                             |
| `invalid_provider`       | Invalid authentication provider.                                                              |
| `invalid_request`        | Invalid login request. Please try again.                                                       |
| `no_verified_emails`     | No verified email addresses found on your account.                                            |
| `oauth_failed`           | OAuth authentication failed. Please try again.                                                |
| `server_error`           | An unexpected server error occurred. Please try again later.                                  |
| `session_missing`        | Session expired or missing. Please try again.                                                 |
| `temporarily_unavailable`| Service temporarily unavailable. Please try again later.                                      |
| Any other / unknown      | `Authentication error: <code>`                                                                |

`user_denied` is deliberately **not** in the table: its message is templated as `Sign-in was cancelled. <retry hint>`, and each surface supplies the retry clause because the recovery path is surface-specific. The JVM IDE port supplies `You can try again from Settings.`; a caller that supplies none gets the default `You can try again.`

The canonical port and the editor extension each keep their **own inline copy** of this table, and both are **narrower**: nine codes each, missing `access_denied`, `invalid_request`, and `temporarily_unavailable` (so all three fall through to `Authentication error: <code>` there). Each of those two hard-codes its own `user_denied` sentence instead of templating it — ``Sign-in was cancelled. You can try again with `jolli auth login`.`` on the canonical port, `Sign-in was cancelled. You can try again from the side panel.` in the editor extension. Their unknown-code fallback is the same `Authentication error: <code>`.

### Result of a successful flow

A single atomic credential write containing:

- The session token (always).
- The tenant URL the credentials belong to (always) — resolved from the minted key's embedded tenant, else the pre-existing on-disk key's embedded tenant, else the sign-in origin. It is **not** simply the origin the browser was pointed at; see **Auth Credential Storage**.
- The product API key (only if the server returned one).

The write is performed via the persistence layer described in **Auth Credential Storage**. A partial write that leaves a token without its associated API key is structurally prevented by routing all these fields through the same atomic update. That layer can also refuse the write outright (an off-allowlist tenant URL, an undecodable key, or a key whose embedded tenant disagrees with the tenant being persisted), and such a refusal surfaces here as a failed sign-in.

## Behavior

### Pre-flight (client-side)

1. Generate the CSRF nonce.
2. Resolve the Jolli origin. On the canonical port and the editor extension the resolver itself enforces the allowlist, so resolution throws for an off-allowlist environment-provided origin; that throw is caught, surfaced as a friendly error, and aborts the flow without committing the nonce. The JVM IDE port's own resolver performs **no** check — it returns whatever the environment variable, system property, or default supplies, and an off-allowlist value is refused later, when the login URL is composed (see **Jolli Origin Allowlist Enforcement**).
3. Load the existing config and decide whether to ask for a fresh key: yes when no product API key is saved, or when the saved key's embedded tenant differs from the target origin; otherwise omit `generate_api_key=true` so a successful sign-in does not rotate a key the user may have configured manually. (The JVM IDE port's user-initiated entry points override this to always ask.)
4. Compose the outbound login URL using the resolved origin, the callback target, the nonce, the surface identifier and version, the conditional `generate_api_key` flag, the machine label (only alongside that flag), and the install identifier — in the surface's pinned order.
5. **Deep-link variant only:** store the nonce as the in-flight expected state, and only after the URL has been composed without throwing. (Storing it earlier would leave an orphaned state if URL composition then threw.) The two loopback variants hold the nonce as a per-attempt value from the moment it is generated, so there is no separate commit step and nothing to orphan.

### Loopback variant — start the server

1. Create an HTTP server bound to `127.0.0.1:0`. A bind failure is a launch failure and is surfaced immediately — the user just asked to sign in and nothing else would tell them.
2. After the OS assigns a port, build the `cli_callback` URL with the actual port number.
3. Open the user's browser to the composed login URL — a detached child process on the canonical port, the host IDE's external-browser facility on the JVM IDE port.
4. Canonical port only: print the login URL to standard output as a fallback for users whose browser does not auto-launch.

Ordering differs between the two: the canonical port composes the login URL and opens the browser from within the server's listen callback, while the JVM IDE port binds and starts the listener **first** and only then, off the UI thread, composes the URL (which is where its allowlist check happens) and opens the browser. A composition or launch failure there tears the listener down and reports a launch failure.

### Deep-link variant — register the URI handler

1. Resolve the OS-registered URI scheme of the host IDE. Forks of the underlying IDE inherit the upstream default for the in-process API, so the scheme is selected by inspecting the host application name (which forks consistently rebrand): Cursor → `cursor`, Windsurf → `windsurf`, VSCodium → `vscodium`, Kiro → `kiro`, Antigravity → `antigravity`, Insiders builds → `vscode-insiders`, default fallback → `vscode`. The "insiders" check runs last so it wins when both the generic and insiders names appear.
2. Compose the callback URI using that scheme, the extension identifier `jolli.jollimemory-vscode`, and the path `/auth-callback`.
3. Open the login URL via the host IDE's external-browser API. If the API returns "did not open" or throws, clear the pending state and surface a user-facing error.

### Receive the callback

The numbered steps below describe the decision tree as the canonical port and the editor extension implement it (including their `400` / `500` HTML responses). The JVM IDE port applies the same *decisions* through the shared runtime but answers the browser with the redirect / plain-text responses tabulated above; its exact evaluation order is spelled out in the subsection that follows.

1. Reject any request whose path is not the accepted route (canonical loopback variant returns `404`; deep-link variant returns a discriminated error; the JVM IDE loopback variant never sees it, because it matches its route by prefix and registers nothing else).
2. If the query carries `error=<code>`, render the mapped HTML error page with status `400`, shut down the server, and surface the mapped message.
3. Otherwise, capture both `code` and `token` from the query string. They are mutually exclusive in practice (a given server emits one or the other).
4. **State validation (code-exchange branch only).** If `code` is present, verify the received `state` is non-empty and equals the expected state under a constant-time comparison. The comparison is performed on the encoded byte buffers, not on the string lengths, to keep an attacker-supplied non-ASCII state from triggering a runtime error in the comparator. On mismatch: render a `400` error page (canonical port) or classify the failure as `invalid_callback` (JVM IDE port), shut down the server, and surface "Invalid sign-in callback (state mismatch). Please try again."
   - **Read-then-clear applies to the deep-link variant only.** The editor extension holds the expected nonce in a mutable field, reads it into a local, and sets the field to `null` *before* comparing, so a second rapid callback finds nothing to match. The two loopback variants hold the expected nonce as a per-attempt local for the duration of the attempt and never null it — their single-shot property comes from tearing the server down (canonical port) or from a compare-and-set guard on the attempt (JVM IDE port) instead.
5. **No state validation on the legacy branch.** Pre-code-exchange servers do not echo state, and demanding it on the `?token=` path would lock those users out. The canonical port and the editor extension log the legacy branch at warning level on every use so residual usage can be tracked; the shared runtime exposes the same hook but the JVM IDE caller does not supply one, so a legacy sign-in on that surface is **not** logged anywhere.
6. **Code-exchange branch.** Invoke the code-exchange routine with the configured Jolli origin and the received `code`. Use the returned `{ token, jolliApiKey? }` (and any `space` when the JVM IDE plugin is the caller).
7. **Legacy branch.** Use `token` directly and read `jolli_api_key` from the query (optional).
8. **Neither.** If neither `code` nor `token` is present and there was no `error`, render a `400` error page, shut down the server, and surface "No authorization code or token received".
9. Persist the token, the resolved tenant URL, and the API key (when one arrived) via the atomic save routine. The save routine validates the tenant URL against the allowlist, validates the API key shape and its embedded origin, and enforces that the key targets the same tenant being persisted; any rejection surfaces as a save error. After the save, render the success HTML page with status `200` and shut down the server.
10. **Best-effort UI updates** (deep-link variant only). After a successful save, set the host IDE's `signedIn` context key to `true`. A failure here is logged and ignored — it must not invalidate the successful save.

#### JVM IDE port — callback decision order

The JVM IDE port hands the raw query string, the expected nonce, and its retry hint to the shared runtime and gets back a resolved outcome plus the URL to redirect the browser to. That decision tree is, strictly in order:

1. **`error=<code>` first**, before any nonce check. Those redirects carry no `state`, so demanding one would report a plain user cancellation as an attack.
2. **`code=<…>`** — the nonce is checked here, and **only** here.
3. **`token=<…>` (legacy)** — accepted with **no nonce check at all**.
4. Neither present — classified `invalid_callback` with "No authorization code or token received".

Step 3 is a deliberate loosening, and its consequence is worth stating plainly: while a sign-in is in flight, a legacy-shaped callback arriving at the ephemeral loopback port from **any** origin is honoured, and its credentials are persisted. The exemption exists because pre-code-exchange servers never echo `state`, so enforcing it would lock those tenants out of sign-in entirely; it disappears when the legacy branch is removed. The same exemption exists on the other two surfaces.

A reported success whose payload omits the token is **not** treated as signed in: it is converted to a failure with its own distinct classification, the user sees a sign-in-failed message, and no signed-in state is published.

### Browser-tab pages (canonical loopback port)

| Status         | Body content                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `200` success  | A small styled card with a check-mark icon, "Login Successful!" headline, the message "Your account has been connected to Jolli.", and a hint that the tab will close automatically. |
| `400` failure  | Same card, with a cross-mark icon and the user-facing failure message.                                                                       |
| `500` failure  | Same card, used when the credential save itself or the code-exchange call threw an unexpected error.                                         |
| `404` not-found | Plain `Not found` text body when the loopback server receives a path other than `/callback`.                                                |

All title and message text is HTML-escaped before being interpolated into the page.

The JVM IDE port's responses are the redirect and plain-text fallbacks tabulated under "Browser-tab response by surface"; it renders no markup of its own.

### Shutdown

The loopback server is forcefully shut down after any terminal callback (success, error, mismatch, missing fields). Force shutdown means destroying open connections so the local process can exit without lingering keep-alive sockets. The deep-link variant has no socket to close.

## State Transitions

The in-flight login attempt has these states:

- **Idle.** No nonce held in memory. No callback handler armed (deep-link variant) or no server listening (loopback variant).
- **Pending.** Nonce held; outbound URL composed; browser opened or attempted. (Loopback variant: server listening; loopback port known.) Awaiting a callback.
- **Resolved.** Either:
  - **Success.** Credentials saved; pending state cleared; server shut down (loopback variant).
  - **Failure.** Pending state cleared; server shut down (loopback variant); user-facing error surfaced.

Allowed transitions:

- Idle → Pending: pre-flight succeeds (origin allowed, URL composed).
- Pending → Resolved (Success): valid `code`-flow callback whose state matches; code exchange succeeds; save succeeds.
- Pending → Resolved (Success): valid `token`-flow callback (legacy fallback); save succeeds.
- Pending → Resolved (Failure): any of — `error=<code>` callback; missing `code` and `token`; state mismatch; code-exchange call throws; save throws.
- Pending → Idle (deep-link variant only, on browser-launch failure): pre-flight committed the pending state but the host IDE's external-browser API rejected the open; the state is cleared so a retry is unambiguous.
- Pending → Idle (JVM IDE port only): the 5-minute login-window expiry fires before any callback arrives. This is **not** a failure transition — the port is released, no error is raised, and nothing is surfaced to the user.
- Pending → Pending (JVM IDE port only, silent supersede): a second sign-in is started while one is in flight. The previous server and expiry timer are torn down with no callback fired; a stale tab that later completes hits either a closed port or the new server with a stale nonce (rejected as a mismatch).

The state machine is single-shot per attempt: there is no retry, no re-arm, and no reuse of the nonce. The user retries by initiating a new flow.

## Notable Behavior

- **State is cleared before it is validated — on the deep-link variant only.** There, the in-flight expected state is read into a local and immediately set to `null` *before* the constant-time compare runs, so an attacker who fires two callbacks (one with the right state, one without) cannot get two attempts at the same nonce. Neither loopback variant does this: each keeps the expected nonce as a per-attempt local and relies on tearing the listener down (canonical) or a compare-and-set guard on the attempt (JVM IDE) for the same single-shot property. (Surprising; intentional; scope matters.)
- **There is no code challenge / verifier exchange anywhere in this flow.** No surface generates or sends one. The nonce echoed on `state` is the only CSRF protection, and it is enforced on the `?code=` shape only. (Notable; do not assume otherwise.)
- **Legacy fallback intentionally bypasses CSRF state, on all three surfaces.** The `?token=` callback shape predates state echoing. Demanding state on that branch would lock users of pre-code-exchange servers out of sign-in. The canonical port and the editor extension log every use at warning level so residual usage can be measured before the branch is removed; the JVM IDE surface logs nothing, because the shared runtime's usage hook is not supplied there — so residual legacy usage on that surface is invisible. (Surprising; and the measurement is incomplete.)
- **Constant-time string compare runs over byte buffers, not over JavaScript string lengths.** UTF-16 code-unit length and UTF-8 byte length disagree on non-ASCII input; a naive comparator that pre-checks string length would crash on attacker-supplied non-ASCII state. The comparator computes UTF-8 buffers, returns `false` on length mismatch, and only then runs constant-time compare. (Notable, defensive.)
- **The OS picks the loopback port.** Binding to port `0` avoids `EADDRINUSE` on machines where another process holds a fixed port the implementation might have hard-coded. (Notable.)
- **The browser child is detached — canonical port only.** The launched browser process is explicitly unreferenced so the command can exit without waiting for the browser to close. The two IDE surfaces hand the URL to the host IDE instead and own no child process. (Notable.)
- **Error pages and success pages are inline HTML — on the canonical port only.** No external CSS or JS resources. The success page contains the only inline script: a 1.5-second `setTimeout` that calls `window.close()` and a 2-second `setTimeout` that updates the visible hint to "You can close this tab now." if the browser refuses to auto-close the tab.
- **The `generate_api_key` flag is conditional on more than "no key saved".** It is also sent when the saved key's embedded tenant differs from the target origin, so a cross-tenant switch provisions in one sign-in instead of two. A same-tenant re-auth still omits it, preventing a successful sign-in from silently rotating a manually configured key (which a subsequent sign-out would then delete). The JVM IDE port's user-initiated "Sign In" entry points force it on regardless, because that click is the user's recovery path from a revoked same-tenant key. (Surprising; intentional.)
- **`device_name` only rides along with a fresh-key request, and it prevents key eviction, not fingerprinting.** It scopes the server's per-user idempotency key, so a second machine's sign-in mints a second key row instead of invalidating the first machine's. Sending it without `generate_api_key=true` would be meaningless, so it is omitted there. (Notable.)
- **The two callback shapes are mutually exclusive in practice.** The handler supports both, but does not version-probe — it just selects the path that matches whichever query parameter is present. (Notable.)
- **An off-allowlist origin is surfaced as a friendly message, not an unhandled exception — but it is caught at different points per surface.** A socially-engineered `JOLLI_URL` environment variable pointing off the allowlist is refused at *resolution* time on the canonical port and the editor extension; the editor extension shows an actionable message ("Unset JOLLI_URL or set it to a trusted Jolli host and retry") and the canonical port surfaces the resolver's own refusal message. The JVM IDE surface has no check in its resolver: the same value flows to login-URL composition, is refused there, and surfaces as a "failed to start login" message. All three abort before the browser is opened. Additionally, the editor extension deliberately **re-reads and re-validates** the origin at callback time (so a mid-flight mutation to an off-allowlist value fails closed), while the canonical port threads the value captured at launch — an intentional, opposite trade-off between the two.
- **A callback with the wrong shape aborts, it does not fall through.** Neither loopback variant treats an unusable callback as "keep listening"; the attempt is resolved as a failure and the listener closes. (Notable.)
- **The in-memory pending state is process-local.** A reload of the host IDE during sign-in invalidates the in-flight attempt by design. The user retries; there is no persistence of an in-flight nonce across restarts. (Notable.)
- **The credential save is one atomic write.** The token, the resolved tenant URL, the API key (when one arrived), and the provider preference all go through a single update, so a partial failure cannot leave a token without its API key (or vice versa). (Notable.)
- **A successful login does not necessarily switch the provider — so one caller writes the provider itself.** The credential save deliberately preserves an existing *explicit* provider choice (see **Auth Credential Storage**), so signing in while the provider is pinned to Anthropic or to the local agent leaves that pin in place. That is why the generation repair ladder (spec 291), whose "switch to Jolli (sign in)" option exists precisely to move a user off a broken local agent, performs an explicit provider write immediately after this flow returns successfully. Without it the user would finish signed in and still pinned to the provider they were trying to escape. (Surprising; intentional.)
- **Best-effort context-key update.** After a successful save, the deep-link variant updates the host IDE's `signedIn` context key. A failure to update the key is logged and ignored — the save is the source of truth.
- **The JVM IDE port's login-window expiry is silent, and exists only to free a socket.** After 5 minutes with no callback it closes the listener and does nothing else — no error, no balloon, no state change the user can observe. Treating it as a failure would punish the common "walked away from the browser tab" case with a scary message. The other two surfaces enforce no login-window expiry at all. (Surprising; documented.)
- **Three implementations still exist, but they no longer diverge in the same places.** *Shared:* the JVM IDE port delegates the whole callback decision tree, the credential write, the error-code table, and its login-URL composition (including the origin-allowlist check) to the shared runtime — it no longer carries its own port of any of that, and its previously separate Kotlin error-code table and CSRF check are gone. *Still divergent:* the canonical loopback server and the editor extension each keep their **own inline copy** of the decision tree, their **own** constant-time comparator, and their **own** narrower error-code table. So there are three tables and three comparators, not one. They also still diverge in nonce length (32 / 32 / 16 bytes), in callback transport (loopback / deep-link), in browser-tab response (own HTML / hosted-page redirect), and in whether a login-window expiry exists. They agree on the overall flow, on `state` being enforced on `?code=` only, on the conditional `generate_api_key` flag, and on the single atomic credential save. (Notable parity facts.)
- **A reported success that omits the token is treated as a failure.** The JVM IDE port refuses to publish signed-in state for a success payload with no token; it converts it to a failure with its own distinct classification (separate from the generic server-error bucket) and shows the sign-in-failed message. (Notable, defensive.)
- **The completion URL is origin-allowlisted before any network work happens.** The JVM IDE flow composes and validates `<jolliUrl>/cli-complete` *before* the code exchange is attempted, because the caller puts that value straight into an HTTP `Location` response header. An off-allowlist or malformed tenant URL therefore fails loudly at the top of the callback rather than reaching a browser redirect — and fails **before** the single-use code is spent. The check runs on the base origin before the page path is appended; the composed URL is not re-checked. (Notable; security-relevant ordering.)
- **There is no explicit carriage-return / line-feed rejection on the redirect target.** Nothing inspects the tenant URL for header-splitting characters. What actually stops it is URL normalization mangling the host into something the origin allowlist then refuses. Do not read this as a CR/LF filter. (Surprising; document the real mechanism.)
- **Any local process that reaches the ephemeral port can abort an in-flight sign-in.** Neither loopback variant validates the HTTP method or pre-screens the query, and both consume the attempt on the first request to reach the callback route. A stray request with a garbage query therefore resolves the attempt as a failure, and the user must start over. The exposure is bounded to processes that can already reach loopback on the OS-assigned port during the seconds-to-minutes the listener is open. (Surprising; a real sharp edge.)

## Shared Behavior

- The HTTP details of the code-for-token exchange (endpoint path, request body, response body, timeout, status-code error mapping) are defined by **CLI Authorization Code Exchange**.
- The shape of the product API key returned by the exchange and how it is decoded are defined by **Jolli API Key Format and Parsing**.
- The allowlist that gates the Jolli origin used to compose the login URL and the exchange URL is defined by **Jolli Origin Allowlist Enforcement**.
- The on-disk storage location, env-var fallbacks, and masking of the saved credentials are defined by **Auth Credential Storage**.
