# Pagefind Search Indexing

## Topic Statement

A static-site search index is generated by invoking the `pagefind` indexer over the documentation site's static-export output, producing an index payload that lives alongside the static files and is read at runtime by the in-page search UI; index failures are tolerated as a non-fatal warning so that a site without search still serves correctly.

## Scope

**In scope:**
- Invocation of the `pagefind` tool from inside the staged build directory.
- The directory it indexes (the static-export output) and where it writes the resulting index.
- Output capture, exit-code handling, and the parsing rule that lifts the pages-indexed count from the runner's text output.
- The two reporting fields the operation returns (success flag plus pages-indexed count) and how the caller surfaces them.
- The graceful-degradation path: a failed indexer run does not abort the build; the site is still publishable without search.
- Where the runtime search UI looks for the index.

**Out of scope:**
- The static-export output's own layout (covered by the build-runner topic).
- Any UI code that consumes the index in the browser.
- The `pagefind` tool's internal scoring, tokenization, or fragment-extraction rules.
- Re-indexing semantics for incremental builds — this topic covers a single one-shot index run.

## Data Contracts

### Run input

The runner takes:

- **build directory** (required, string): the staged project build directory whose static-export output will be indexed. The `pagefind` tool is run with this as its working directory.

### Run result

The runner returns:

- **success** (required, boolean): true if the indexer exited zero, false otherwise.
- **output** (required, string): the captured combined stdout and stderr text from the indexer.
- **pages indexed** (optional, integer): the count parsed out of the indexer's output, present only on success and only when the parse matched.

### Index location

- **input directory passed to the indexer**: the static-export output directory at `out/`, relative to the build directory.
- **output directory the indexer writes**: an explicit `out/_pagefind/` directory under the static-export output.

### Search-index file layout

The indexer writes its index files into the `out/_pagefind/` directory it was instructed to create. The runtime search UI in the rendered pages looks for the index at the relative path `_pagefind/` from the site root, which matches the directory the indexer wrote.

## Behavior

### Invocation

1. Compose the indexer's argument list: the literal token `pagefind`, followed by `--site out`, followed by `--output-path out/_pagefind`.
2. Run the indexer through the npm-ecosystem command runner (`npx`) in the build directory, with both standard streams piped for capture.
3. Coerce captured stdout and stderr to strings, filter out empty streams, and join the survivors with a newline into a single output string.
4. If the exit code is zero: parse the output for the pages-indexed count (see below) and return success-true with the parsed count attached if found.
5. Otherwise return success-false with the captured output. No pages-indexed count is included on failure.

### Pages-indexed parsing

A single regular expression looks for a sequence of digits followed by whitespace and the word "page" (case-insensitive, optionally pluralized). The first match is captured, parsed as a base-10 integer, and used as the pages-indexed count.

If no match is found on a successful run, the pages-indexed field is omitted from the result; the run still reports success.

### Caller-side reporting

The caller surfaces the run result. On success the pages-indexed count is presented to the user as a status line. On failure the captured output is logged as a warning and the build is allowed to proceed — the site still publishes, but without an in-page search index. The build's own success/failure is unaffected by the indexer's outcome.

### Graceful degradation

A failed indexer run leaves the static-export output untouched (the indexer adds files; it does not rewrite the rendered HTML). The runtime search UI handles a missing index by silently disabling its search dropdown. So the user-visible consequence of an indexer failure is exactly "no search bar functionality on the deployed site" — every other page is still served correctly.

## Notable Behavior

### One-shot indexing

The runner indexes once per build invocation. There is no incremental mode — the indexer always re-reads the entire static-export output and writes a fresh index payload. This matches the build flow's batch nature.

### Working directory binding

The indexer runs with its working directory set to the build directory. The relative `out/` path it indexes therefore resolves to the build's static-export output, regardless of where the caller invoked the build from.

### Explicit output path

The output path is passed explicitly rather than relying on the indexer's default. The caller pins the directory to `out/_pagefind/` so the runtime search UI's lookup path (`_pagefind/` from the site root) reliably finds it.

### Stdout-and-stderr capture

Both standard streams are captured and combined into a single output string. The indexer prints its progress and pages-indexed summary to stdout, but error messages may go to stderr; combining the streams ensures both are available to the caller for failure-path display and to the parser for the count extraction.

### Empty-stream filtering

Stream concatenation filters out streams that produced no bytes so the joined output never starts or ends with a stray newline that came from concatenating an empty stream against a non-empty one.

### Exit-code policy

Any non-zero exit code is treated as failure. There is no per-error special handling; the runner simply returns the captured output verbatim and lets the caller decide whether to log it as a warning or escalate.

### Best-effort count parsing

The pages-indexed count is best-effort: the runner does not fail the run if the regular expression does not match. A successful indexer run with unrecognized output shape simply yields a result with the count omitted, and the caller's status line accommodates a missing count.

### Windows command-shape handling

The npm-ecosystem command runner ships on Windows as a batch script. Spawn invocations on Windows therefore set the shell-mode option and pass the entire command (including arguments) as one string with an empty arguments array, sidestepping the deprecation warning that fires when shell mode coexists with a separate arguments array.

## Shared Behavior

- **npm runner** — sibling component that runs the build operation that produces the static-export output the indexer reads.
- **Static-export output directory** — the on-disk artifact the indexer's input path resolves to.
- **Runtime search UI** — emitted as part of the rendered pages; reads the index from the path the runner wrote.
- **Build directory layout** — the staged project that holds both the static-export output and the indexer's working-directory binding.
