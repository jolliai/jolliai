# 208. Trace Context Correlation Across Logs and Outbound Calls

## Topic Statement

A Jolli-private correlation identifier that ties every log line and outbound HTTP request belonging to one logical operation into a single grep-able unit, propagates across OS-process boundaries via both a persisted queue field and an environment variable, and is guaranteed to be present on every outbound request regardless of whether an ambient operation scope is active.

## Scope

**In scope:**

- The identifier format (trace id, span id, wire header name and value shape).
- The all-zero sentinel that the backend rejects and this layer never emits.
- The in-process ambient scope mechanism and its scoping / nesting rules, in both the async (TypeScript) and synchronous-threaded (Kotlin) implementations.
- The escape hatch that strips an ambient id from a deliberately unrelated child scope.
- The three cross-process propagation paths: environment variable on worker spawn, persisted queue entry field, and freshly minted standalone value for code outside any scope.
- Every entry point that opens a trace scope: CLI main, all git hooks (post-commit, post-rewrite, post-merge), the queue worker main, sync-engine rounds, and all UI-layer action dispatchers (VS Code webview handlers, IntelliJ push and binding dialogs).
- Every outbound call site that attaches the header: LLM proxy, backend sync, auth exchange, and all IntelliJ Jolli API calls.
- The log-line stamping rule: one `[trace=<id>]` tag per line whenever an ambient scope is active.

**Out of scope:**

- The backend's handling of the header (how the backend builds a span tree from received trace values is not specified here).
- The log file format beyond the trace tag (see spec 131).
- The LLM proxy call structure beyond the header (see specs 08–09).
- The queue entry structure beyond the `traceId` field (see the queue-worker spec).
- Telemetry event emission (uses the same trace scope but is specified separately).

## Data Contracts

### Identifier formats

| Component | Length | Encoding | Sentinel |
|-----------|--------|----------|---------|
| Trace id | 32 lowercase hex chars (16 bytes) | cryptographically random | all-zero string (`"0"×32`) |
| Span id | 16 lowercase hex chars (8 bytes) | cryptographically random | all-zero string (`"0"×16`) |

Both generators loop until the produced value is not the all-zero sentinel. The probability of hitting the sentinel is astronomically low, so the loop is a safety net, not a performance concern.

### Wire header

| Field | Value |
|-------|-------|
| Header name | `x-jolli-trace` |
| Header value | `<traceId>-<spanId>` |

The format is **Jolli-private**: it does not use the W3C `traceparent` header name and omits the W3C `00-` version prefix and `-01` trace-flags suffix. This is intentional — standards-aware middleboxes would attempt to parse `traceparent` and may reject or modify a non-conformant value. The two-segment shape `<traceId>-<spanId>` is the complete wire format; no additional segments are appended.

The `<spanId>` segment is a flat per-request marker. A fresh span id is generated for each individual outbound call; there is no client-side parent/child span hierarchy. Correlation by the consumer (backend) is by `traceId`, and the backend is responsible for any span tree it builds.

This header contract is shared identically across three codebases: the CLI/VS Code TypeScript bundle, the IntelliJ Kotlin plugin, and the Jolli backend (`jolli-common`). Any change must be applied in lockstep across all three.

### Environment variable

| Name | Value |
|------|-------|
| `JOLLI_TRACE_ID` | A 32-hex trace id (must pass the same format + non-zero validity check). |

When a process receives this variable, it adopts the id as its ambient trace; if the value is absent, malformed, or the all-zero sentinel, the process generates a fresh id. This is the only environment-based propagation channel.

### Persisted queue entry field

Queue entries for git operations carry an optional `traceId` string field. When the enqueuing hook has an active ambient scope, the current trace id is written into this field. The field is absent for entries created before this feature existed or by code paths that have no active scope.

## Behavior

### Id generation

A trace id is generated by drawing 16 cryptographically random bytes and encoding them as 32 lowercase hex characters. If the result is all-zero, the draw is repeated. A span id follows the same algorithm with 8 bytes producing 16 hex characters. Both are ephemeral — they are never stored beyond the lifetime of the scope or the single outbound request that uses them.

### Ambient scope (TypeScript / VS Code)

The ambient scope is backed by an async-local storage cell, which propagates the trace id automatically across `await` boundaries within the same async call tree — no manual threading of a parameter is needed.

Opening a scope:
1. A caller opens a scope by calling the scope-enter function with an optional trace id string.
2. If the provided id is a well-formed 32-hex, non-zero string, it is adopted; otherwise a fresh id is generated.
3. The id is stored in the async-local cell and the supplied callback is called inside that cell's context.
4. When the callback returns (or its promise settles), the cell reverts to whatever value it held before — restoring the enclosing scope, or becoming empty outside any scope.

Nested scopes override the inner subtree's id for their duration and restore the outer id on exit.

Reading the ambient id: any code running inside a scope can read the current id without parameters. Code running outside any scope receives `undefined`.

Clearing the scope deliberately: a second mechanism exits the async-local cell entirely for the duration of a callback, making the ambient id `undefined` even when called inside an active scope. This is used when spawning work for a different repository so the current operation's trace id does not leak into the unrelated child.

### Ambient scope (Kotlin / IntelliJ)

The ambient scope is backed by a `ThreadLocal`. Because IntelliJ plugin work is synchronous and single-threaded per operation, a thread-local provides the same isolation as an async-local in the TypeScript implementation.

Opening a scope: the previous thread-local value is saved, the adopted or freshly generated id is set, the callback runs, and the previous value is restored in a `finally` block — whether by re-setting it if non-null or removing it if null. Nested scopes therefore behave identically to the TypeScript implementation: inner overrides, outer restores.

Reading the ambient id: thread-local read, returns null outside any scope.

There is no explicit "exit without trace" mechanism in the Kotlin implementation. The IntelliJ plugin does not spawn work for different repositories within the same thread during an operation, so there is no use case requiring it.

### Header construction

Two header construction modes exist, both producing the same wire format:

**Ambient mode** (`currentTraceHeader`): reads the ambient trace id and pairs it with a freshly generated span id. Returns `undefined`/null when no scope is active. Used by call sites inside an operation scope (hooks, queue worker, sync rounds, UI action handlers) so the request is identified with that operation's trace.

**Standalone mode** (`newTraceHeader`): generates a fresh trace id and a fresh span id, with no reference to any ambient state. Used directly by call sites outside any operation scope, or as a fallback when `currentTraceHeader` returns `undefined`/null.

The fallback pattern at every outbound call site is `currentTraceHeader() ?? newTraceHeader()`. This guarantees the header is **always present** on every outbound request — there is no code path that omits `x-jolli-trace`.

### Log-line stamping

Every logger (TypeScript CLI, VS Code, IntelliJ) reads the ambient trace id at the moment a log record is formatted. If an id is present, a tag ` [trace=<id>]` is appended after the module name and before the message body. If no scope is active, the tag is omitted entirely. The trace id is passed into the formatting function explicitly (not read inside it) in the TypeScript implementations, keeping the formatter pure and testable.

### Entry-point trace seeding

Every process entry point opens a trace scope as its outermost action:

| Entry point | Seed behavior |
|-------------|--------------|
| CLI main | Reads `JOLLI_TRACE_ID` from the process environment; adopts if valid, else mints a fresh id. One trace per CLI invocation. |
| Post-commit hook | Reads `JOLLI_TRACE_ID`; adopts or mints. The entire hook body, including queue-entry creation and worker launch, runs inside this scope. |
| Post-rewrite hook | Same as post-commit. Stamps the scope's id onto every queue entry it creates (amend entries and all rebase-pick / rebase-squash entries), so all rebased commits in one rebase share a single trace id. |
| Post-merge hook | Same as post-commit. |
| Queue worker main | Reads `JOLLI_TRACE_ID` (set by the launcher; see below); adopts or mints. This id covers worker startup, lock acquisition, chain-spawn decisions, and all process-level log lines. It is overridden per queue entry (see below). |
| Sync engine round | Mints a fresh id with no env-var adoption. Sync rounds are not tied to a git operation, so each round is an independent trace. |
| VS Code webview dispatch | Mints a fresh id for each incoming webview message dispatch. Push, regenerate, edit-topic, and related actions each run inside their own scope. |
| VS Code binding chooser | Mints a fresh id for the binding-creation action. |
| IntelliJ LLM call | Mints a fresh id wrapping the LLM invocation. Every LLM call is a self-contained trace. |
| IntelliJ push action | Mints a fresh id on the pooled worker thread, covering all `pushToJolli`/`listSpaces` calls and their logs. The `withTrace` must be set on the actual worker thread because a `ThreadLocal` is thread-bound. |
| IntelliJ binding dialog confirm | Mints a fresh id on the pooled worker thread for the `createBinding` call. |

### Cross-process trace propagation

**Hook → worker (via environment variable):**

When a hook spawns the detached queue worker, it reads the current ambient trace id. If one is active, it sets `JOLLI_TRACE_ID=<traceId>` in the child process's environment. The worker's main function reads this variable at startup and opens its process-level trace scope with it. This ensures the worker's startup and lock-acquisition log lines carry the same id as the hook that spawned it.

If no ambient trace is active at spawn time, `JOLLI_TRACE_ID` is not set, and the worker mints a fresh id for its process-level scope.

**Hook → worker (via persisted queue entry):**

For each queue entry the hook processes (post-commit, post-rewrite, post-merge), the ambient trace id is written into the entry's `traceId` field before the entry is persisted to disk. When the queue worker drains the entry, it opens a new inner trace scope using `op.traceId`, if present, falling back to the worker's own ambient id if the field is absent (compatibility with entries written before this feature was added). This inner scope covers the LLM call, the summary write, and all backend pushes for that specific commit — so a single commit's work is identified by the trace id that was active when the commit hook ran.

**Worker → sibling-repo worker (trace isolation):**

When the queue worker needs to wake a pending worker for a different repository, it deliberately clears the ambient trace before launching that worker. This prevents the current operation's trace id from leaking via `JOLLI_TRACE_ID` into work that belongs to an unrelated repository.

### Outbound call sites

Every outbound HTTP / HTTPS call site applies the `currentTraceHeader() ?? newTraceHeader()` pattern:

| Call site | Notes |
|-----------|-------|
| LLM proxy call (CLI) | Header added alongside auth, client-version, and tenant headers. |
| Backend sync / Memory Bank sync call (CLI) | Header added per request inside the sync round's trace scope. |
| CLI auth exchange | Header added to the single-request OAuth token exchange. |
| IntelliJ Jolli API — push article | Header added per request. |
| IntelliJ Jolli API — delete article | Header added per request. |
| IntelliJ Jolli API — list spaces | Header added per request. |
| IntelliJ Jolli API — create binding | Header added per request. |
| IntelliJ Jolli API — additional endpoints | Same pattern; all request builders in the Jolli API client apply the header. |
| VS Code push service | Header added to the `fetch` call for article push. |

No outbound call site omits the header. Any new call site that does not apply this pattern breaks the correlation guarantee.

## State Transitions

```
[process starts]
  ambient trace = undefined/null (no scope active)

[entry point seeds the scope]
  reads JOLLI_TRACE_ID env var
  if valid → adopt; else → generate fresh
  ambient trace = <adopted or fresh id>

[hook enqueues a git operation]
  reads ambient trace id
  writes traceId field into the queue entry JSON

[hook spawns the queue worker]
  reads ambient trace id
  if present → sets JOLLI_TRACE_ID=<id> in child env
  child process starts; adopts JOLLI_TRACE_ID or mints fresh

[worker drains a queue entry]
  opens inner scope: op.traceId ?? worker's own ambient id
  ambient trace = entry-specific id
  all log lines and outbound calls within this entry carry entry's id
  inner scope closes; ambient reverts to worker's process-level id

[worker wakes a sibling-repo worker]
  ambient trace temporarily cleared (exits async-local cell)
  launches sibling worker — no JOLLI_TRACE_ID propagated
  ambient trace restored to current value after launch

[sync engine starts a round]
  opens fresh trace scope (no env adoption)
  ambient trace = fresh id for this round
  scope closes when round completes

[VS Code webview dispatch]
  opens fresh trace scope per incoming message
  ambient trace = fresh id for this action
  scope closes when dispatch completes

[outbound HTTP call]
  currentTraceHeader() read → if ambient active: traceId + fresh spanId
  if no ambient: newTraceHeader() → fresh traceId + fresh spanId
  x-jolli-trace header attached to request
  scope unchanged (span id is ephemeral, not stored)

[process exits]
  in-flight async-local scopes may still be active; they drain naturally
```

## Notable Behavior

- **The header is unconditionally present on every outbound request.** The fallback to `newTraceHeader()` means even a one-shot background call that never opened an operation scope still carries a unique, traceable identifier. The backend can always find the request in its logs via the header value.

- **Span ids are ephemeral and not stored.** Only the trace id is carried in the queue entry, the environment variable, and the log lines. The span id exists only long enough to construct the wire header value for one request; it is not recorded anywhere, not logged, and not adoptable by downstream processes.

- **Nested scope adoption overrides the inner subtree only.** If a queue worker has process-level trace A, and a drained entry has trace B, the entry's processing runs under B, and after the entry completes the worker returns to A. This is automatic — no manual restore is needed.

- **All rebase commits in one rebase share one trace id.** The post-rewrite hook opens one outer scope for the entire rebase operation and stamps that same id onto every queue entry it creates. From a correlation standpoint, a rebase is one logical operation regardless of how many commits it touches.

- **The IntelliJ `withTrace` must be called on the worker thread, not the EDT.** Because the Kotlin ambient mechanism is a `ThreadLocal`, code that opens a scope on the Event Dispatch Thread and then dispatches work to a pooled thread will not propagate the id. The IntelliJ push and binding operations call `withTrace` inside the `executeOnPooledThread` lambda, not before it.

- **The IntelliJ Kotlin implementation does not support `runWithoutTrace`.** The sibling-repo trace isolation pattern (clearing the ambient before an unrelated launch) is not present in the Kotlin surface because the IntelliJ plugin does not launch cross-repo workers.

- **Adopting the all-zero sentinel is an explicit error case.** The validity check rejects it so that accidental propagation of a zeroed-out buffer (a common memory-init pattern) does not cause the backend to log a traceable-looking but invalid and non-unique id. The backend independently rejects it; the client mirrors that rejection at adoption time.

- **The env-var adoption path validates format.** A parent that sets `JOLLI_TRACE_ID` to anything other than 32 lowercase hex characters — including an empty string or the all-zero sentinel — causes the receiving process to mint a fresh id rather than adopt the malformed value. This prevents a misconfigured external orchestrator from injecting a bad id.

- **Every entry point is covered.** There is no "untraced" entry in normal operation. A process that somehow runs without opening a scope (e.g., a hook invoked outside any scope) still produces traceable outbound requests via the `newTraceHeader()` fallback; log lines simply lack the `[trace=…]` tag until a scope is opened.
